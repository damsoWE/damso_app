# 이슈 생성 + 브랜치 연결

팀 흐름: **이슈 → 브랜치 → 커밋 → PR**. 규칙 원본은 `CLAUDE.md`의 "Git Workflow".
인자 예:
- `/new-issue 백엔드 features F1` — 백엔드 기능 목록의 F1을 프론트 이슈로 만든다
- `/new-issue 로그인·회원가입 화면 구현`
- `/new-issue fix 토큰 갱신 실패 시 로그아웃 안 됨`

## 절차

0. **백엔드 기능 번호가 있으면** (인자에 `F1`~`F5` 같은 `F<숫자>`가 있을 때) 먼저 기능 정의를 읽는다.
   - 백엔드 레포가 비공개라 `gh`로 읽는다 (로컬 경로에 의존하지 않는다):
     ```bash
     gh api "repos/damsoWE/damso_server/contents/docs/features.md" -H "Accept: application/vnd.github.raw"
     ```
   - 해당 `## F<번호>.` 섹션과 맨 위 상태 표의 그 행(기능명·spec 경로·상태)만 사용한다.
   - 초안은 **프론트가 화면에서 보고 하는 것** 기준으로 옮긴다. 서버 내부 규칙(암호화 저장, 감사 로그 기록 등)과 기술 이름은 뺀다.
     - 제목: `[Feat] F<번호> <기능명> 화면`
     - `어떤 기능인가요?`: 섹션의 **왜**를 프론트 관점으로 1~3문장
     - `작업 상세 내용`: **사용자 시나리오**·**결정됨**에서 화면·상태·입력 검증 항목을 체크리스트로. 로딩/빈 목록/오류 같은 상태 화면도 항목으로 넣는다
     - `유의사항`: **지켜야 할 것**의 관련 원칙, `대응 백엔드 spec: <상태 표의 spec 경로>`(미생성이면 "미생성"), `Figma: (프레임 링크 필요)`, **미정** 항목이 있으면 "clarify에서 결정"으로 옮긴다
   - 가져오지 못하면(로그인·권한 문제) 이유를 알리고 사용자에게 섹션 내용을 붙여 넣어 달라고 한다. 내용을 추측해서 만들지 않는다.
   - 여러 번호(`F1 F2`)가 오면 번호마다 이슈 하나씩 만든다. 승인은 한 번에 받되 브랜치 연결은 **하나만** 고르게 한다(체크아웃이 하나뿐이므로).
   - 기능 하나를 프론트 여럿이 나눠 맡는 경우(예: 화면별)에는 사용자가 지정한 범위로 이슈를 쪼갠다. 지정이 없으면 기능 하나 = 이슈 하나.

1. **종류 판단** — 기능이면 `Feat`, 수정이면 `Fix`. 인자 첫 단어가 `fix`면 Fix, 그 외는 Feat. 애매하면 사용자에게 한 번만 묻는다.
2. **초안 작성** — `.github/ISSUE_TEMPLATE/feature_request.md`의 섹션 순서를 그대로 쓴다.
   - 제목: `[Feat] <요약>` / `[Fix] <요약>` (한국어, 한 줄)
   - `요청 유형`: 해당 항목 하나만 `- [x]` (새로운 기능 추가 / 기존 기능 개선 / 성능 개선). Fix는 "기존 기능 개선"
   - `어떤 기능인가요?`: 1~3문장, 무엇/왜 중심. 기술 스택은 쓰지 않는다
   - `작업 상세 내용`: `- [ ]` 체크리스트로 3~7개. 확실하지 않은 항목은 지어내지 말고 `- [ ] TODO`로 둔다
   - `유의사항`: 관련 constitution 원칙·Figma 프레임 링크·대응 백엔드 이슈/spec 경로가 있으면 적고, 없으면 비운다
   - 문의·답변 본문, 토큰, 개인정보 등 민감한 값은 이슈에 넣지 않는다
3. **확인** — 초안(제목·본문·라벨·브랜치 이름)을 사용자에게 보여 주고 **승인받은 뒤에만** 생성한다. 이슈는 팀 전체에 보이는 외부 게시물이다.
4. **이슈 생성** — 본문을 임시 파일에 저장하고 만든다. 라벨: Feat → `enhancement`, Fix → `bug`.
   ```bash
   gh issue create --title "[Feat] …" --body-file <임시 파일> --label enhancement
   ```
   출력된 URL의 번호를 기억한다.
5. **브랜치 연결** — 작업 트리에 커밋 안 된 변경이 있으면 먼저 알리고 진행 여부를 묻는다. 없으면:
   ```bash
   git switch main
   git pull
   gh issue develop <번호> --name features/<영문-kebab-case> --base main --checkout
   ```
   - 브랜치 이름: 기능은 `features/…`, 수정은 `fix/…`. 영문 소문자·숫자·하이픈만 쓴다 (예: `features/f1-auth-signup`)
   - 사용자가 "이슈만"이라고 하면 이 단계는 건너뛴다
6. **결과 보고** — 이슈 URL, 브랜치 이름, 다음 할 일(예: `/speckit-specify`)을 짧게 알린다.

## 하지 않는 것

- 사용자 승인 없이 이슈를 만들지 않는다.
- 커밋·푸시·PR은 이 스킬에서 하지 않는다 (사용자가 따로 요청할 때만).
- 이슈 제목·본문·커밋에 Claude 등 AI 기여자 표시를 넣지 않는다.
