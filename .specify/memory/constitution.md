# 담소(DAMSO) 프론트엔드 Constitution

> 원칙 I~VIII(Core Principles)은 백엔드 레포 `damsoWE/damso_server`의 constitution v1.2.0과 **글자까지 동일**하다. 두 레포에서 함께 개정한다(Governance 참고).
> 원칙 문구는 서버 기준으로 쓰여 있으므로, 앱에서 지켜야 할 구체 규칙은 아래 "프론트엔드에서의 적용"에 정리한다.

## Core Principles

### I. 연락처 미수집

- 전화번호·주소 등 연락처를 수집하거나 저장하지 MUST NOT 한다.
- `users` 테이블을 포함한 어떤 테이블에도 연락처 컬럼을 두지 MUST NOT 한다.
- 학부모와 교사 어느 쪽도 API를 통해 상대의 연락처를 알 수 없어야 MUST 한다.
- 이메일은 연락처로 보지 않는다. 가입 인증·로그인 식별용 최소 인증 수단으로만 쓰며, 다른 사용자에게 노출하지 MUST NOT 한다.

근거: 교사 개인번호 노출 문제를 기능이 아닌 데이터 부재로 해결한다. 없는 데이터는 유출되지 않는다.

### II. 가명화 게이트웨이 경유

- 외부 LLM으로 나가는 모든 텍스트는 가명화 게이트웨이를 거쳐야 MUST 한다. 우회 호출 경로를 두지 MUST NOT 한다.
- 가명화 대상: 학생명·보호자명·교사명·학교명·학급, 그리고 패턴 탐지로 찾은 전화번호·주소.
- 복원표는 요청 처리 중 메모리에만 존재해야 MUST 하며, DB·캐시·파일 저장과 로그 출력을 MUST NOT 한다.

근거: 아동·청소년 개인정보가 외부 API 경계를 넘지 않음을 구조로 보장한다.

### III. 원문 보존과 열람 감사 (append-only)

- 문의 원문은 암호화해 저장해야 MUST 한다.
- 원문·정제본·처리 이력에 대한 수정·삭제 API를 제공하지 MUST NOT 한다.
- 원문 열람은 열람자·대상·시각을 감사 로그에 기록해야 MUST 한다. 감사 로그 역시 append-only다.

근거: "검열" 오해를 차단하고, 교권보호위원회 등에 제출할 기록의 무결성을 확보한다.

### IV. 긴급 우선 — 긴급 fail-open, 일반 fail-closed

- 학생 안전·학대·자해 관련 긴급 판정은 LLM 호출 이전에 규칙 기반으로 수행해야 MUST 한다.
- 긴급 판정은 보수적으로 한다. 의심되면 정제를 건너뛰고 교사에게 즉시 전달·알림한다(fail-open).
- 긴급 경로는 LLM·외부 API 장애와 무관하게 동작해야 MUST 한다.
- 일반 정제가 실패하거나 출력 검증에 실패하면 1회 재시도 후 "원문 확인 필요" 상태로 전이하고 교사에게 알린다(fail-closed). 검증되지 않은 정제 결과를 교사에게 보여주지 MUST NOT 한다.

근거: 외부 장애가 안전 사안의 전달을 막지 못하게 하고, 잘못된 정제가 사실처럼 전달되는 것을 막는다.

### V. 제안만 한다 — 교사 답변 자동 발송 없음

- 답변 점검 결과는 제안으로만 제공해야 MUST 한다.
- 교사 명의의 답변을 교사의 명시적 전송 행위 없이 학부모에게 발송하는 경로를 두지 MUST NOT 한다.
- 시스템이 교사 답변을 대신 작성하거나 수정해 저장하지 MUST NOT 한다.
- 시스템 안내(접수 확인·처리 상태·긴급 전달 안내·응답 가능 시간 안내)는 교사 명의와 구분해 시스템 발신으로 표시해야 MUST 하며, 교사의 판단이나 약속처럼 보이는 문구를 포함하지 MUST NOT 한다.
- 시스템 안내는 사전 정의된 고정 문구로만 구성해야 MUST 한다. LLM이 생성한 텍스트를 학부모에게 직접 발신하지 MUST NOT 한다.

근거: AI 오작동이 곧 실제 발신이 되는 사태를 차단하되, 필요한 시스템 안내는 교사의 책임 영역과 분리한다.

### VI. 민감정보 비노출 (로그·에러)

- 문의·답변 본문과 정제 결과를 애플리케이션 로그에 출력하지 MUST NOT 한다. 로그에는 식별자(UUID)와 상태만 남긴다.
- 에러 응답에 스택트레이스·예외 클래스명·내부 경로·SQL을 노출하지 MUST NOT 한다. 전역 예외 처리로 에러 코드와 일반 메시지만 반환한다.

근거: 로그와 에러 응답은 가장 흔한 유출 경로다.

### VII. UUID 식별자와 건별 소유권 검증

- 외부에 노출되는 모든 식별자는 UUID여야 MUST 한다. 순번 ID를 API에 노출하지 MUST NOT 한다.
- 모든 리소스 접근은 서비스 계층에서 건별로 소유권·권한을 검증해야 MUST 한다.
  - 학부모: 본인이 작성한 문의와 그 답변만
  - 교사: 담당 학급의 문의만
  - 학교 관리자(도입 시): 메타데이터만, 내용 열람 권한 없음
- 요청 본문·파라미터로 받은 역할·사용자 ID를 권한 판단에 사용하지 MUST NOT 한다. 인증 주체와 DB 기준으로만 판단한다.

근거: 수평 권한상승(타인 문의 조회)을 단일 지점에서 차단한다.

### VIII. 안전한 기본값

- 시크릿(DB 비밀번호, 암호화 키, JWT 서명 키, LLM API 키)은 환경변수로만 주입해야 MUST 한다. 코드·설정 파일에 하드코딩하지 MUST NOT 한다.
- 필수 시크릿이 없거나 형식(키 길이 등)이 맞지 않으면 애플리케이션은 기동을 거부해야 MUST 한다.
- 기본 계정·기본 비밀번호를 제공하지 MUST NOT 한다.

근거: 공개 저장소를 그대로 배포했을 때 설치 실수가 유출로 이어지는 경로를 막는다.

## 프론트엔드에서의 적용

| 원칙 | 앱에서 지킬 것 |
|---|---|
| I. 연락처 미수집 | 가입·프로필·문의 어떤 화면에도 전화번호·주소 입력란을 두지 MUST NOT 한다. 상대방의 이메일을 화면에 표시하지 MUST NOT 한다. |
| III. 원문 보존 | 보낸 문의·답변을 수정·삭제하는 UI를 두지 MUST NOT 한다. 원문은 서버 API로만 열람하고 기기에 캐시·저장하지 MUST NOT 한다. |
| IV. 긴급 우선 | 긴급 문의 표시·알림을 사용자가 끌 수 있는 설정을 두지 MUST NOT 한다. "원문 확인 필요" 상태에서는 정리본을 표시하지 MUST NOT 한다. |
| V. 제안만 한다 | 답변 점검 결과를 자동 반영하거나 자동 전송하는 동작을 두지 MUST NOT 한다. 시스템 안내 메시지는 교사 메시지와 시각적으로 구분해 표시해야 MUST 한다. |
| VI. 민감정보 비노출 | 문의·답변 본문을 `print`·`debugPrint`·로깅·크래시 리포트·분석 이벤트로 내보내지 MUST NOT 한다. 서버 에러 응답은 `message`만 사용자에게 보여 준다. |
| VII. 식별자·권한 | 화면 접근 제어는 go_router 리다이렉트 한 곳에서 한다. 단, 권한 판단의 최종 기준은 서버이며 앱의 숨김 처리를 보안 수단으로 삼지 않는다. |
| VIII. 안전한 기본값 | API 키·토큰 등 시크릿을 앱 코드·`env/*.json`·에셋에 넣지 MUST NOT 한다. 앱에는 서버 주소 같은 공개 설정만 둔다. |

## 프론트엔드 보안 요건

- **토큰 보관**: Refresh Token은 OS 보안 저장소(`flutter_secure_storage` — iOS Keychain / Android Keystore)에만 저장해야 MUST 한다. Access Token은 메모리에만 두고 디스크에 저장하지 MUST NOT 한다.
- **토큰 주입·갱신 단일 지점**: Authorization 헤더 주입과 401 시 토큰 갱신은 dio Interceptor 한 곳에서만 처리해야 MUST 한다. 갱신이 실패하면 저장된 토큰을 지우고 로그인 화면으로 보낸다.
- **렌더링**: WebView 및 HTML 렌더 패키지를 사용하지 MUST NOT 한다. 문의·답변 본문은 일반 텍스트 위젯으로만 표시한다.
- **릴리스 빌드**: `flutter build --obfuscate --split-debug-info=<dir>`로 빌드해야 MUST 한다. 디버그 심볼은 저장소에 커밋하지 않는다.
- **에러 표시**: 서버의 `ErrorResponse`(`code`, `message`, `fieldErrors`)만 사용하고, 예외 객체·스택트레이스를 화면에 표시하지 MUST NOT 한다.

## 아키텍처

- 코드 구조는 다음을 따른다.
  ```
  lib/app                                  # 루트 위젯, 라우터(go_router)
  lib/core                                 # config · network(dio) · storage
  lib/features/<기능>/
  ├── domain                               # 모델 · Repository 인터페이스
  ├── data                                 # 실서버 Repository 구현
  └── presentation                         # 화면 · 상태(Riverpod)
  lib/mock                                 # mock Repository override
  ```
- 화면(presentation)은 `domain`의 Repository 인터페이스에만 의존해야 MUST 한다. `data` 구현을 직접 참조하지 MUST NOT 한다.
- 실서버와 mock 구현은 Riverpod provider override로 교체한다. 화면 코드를 바꾸지 않고 `lib/main_mock.dart`로 mock 실행이 가능해야 한다.
- mock에는 정상 응답만 넣지 않는다. 401(토큰 만료 → 갱신), 403(남의 문의), 정제 진행 중 → 완료, "원문 확인 필요", 긴급 문의 케이스를 포함해야 MUST 한다.

## 개발 흐름과 품질 게이트

- **기획서 취급**: `docs/아기하마_개발기획서.pdf`는 참고 자료이며 개발 중 바뀔 수 있다. 기획서와 달라지는 결정은 백엔드 레포 `docs/decisions.md`에 기록한다. 이 constitution의 원칙은 기획서 변경으로 바뀌지 않는다.
- **명세 주도 개발**: 기능은 spec-kit 흐름(specify → clarify → plan → tasks → implement)을 따른다. spec에는 무엇/왜만 쓰고 기술 스택은 plan에서 정한다. 각 spec에는 **대응하는 백엔드 spec 경로**를 적어야 MUST 한다.
- **Contract-first**: API 명세의 원본은 백엔드 레포의 `docs/api/openapi.yaml`이다. 앱의 `docs/api/openapi.yaml`은 사본이며 직접 수정하지 MUST NOT 한다. 백엔드 공지를 받으면 `/fetch-api <태그>`로 받아 온다.
- **머지 게이트**: AI 생성 코드를 포함한 모든 변경은 PR 리뷰와 CI 보안 검증(Gitleaks 등)을 통과해야 머지한다.
- **검증**: `flutter analyze`와 `flutter test`를 통과해야 한다. 실패를 숨기거나 우회하지 않는다.
- **문서 언어**: spec·plan·tasks 등 프로젝트 문서는 한국어로 작성한다.

## Governance

- 이 constitution은 기획서, 개별 spec, 에이전트 지침(`CLAUDE.md`, `AGENTS.md`)보다 우선한다. 충돌 시 constitution을 따른다.
- **개정 절차**: 개정은 PR로만 한다. PR에는 변경 이유와 영향받는 spec·코드 목록을 적고 리뷰 승인을 받는다.
- **원칙 I~VIII 변경**: 백엔드 레포(`damsoWE/damso_server`) constitution과 같은 원칙이므로 두 레포를 같은 시점에 함께 개정해야 MUST 한다. 이 레포에서만 고치지 않는다.
- **버전 정책**: 원칙 삭제·재정의는 MAJOR, 원칙·섹션 추가나 실질적 확장은 MINOR, 문구 정리는 PATCH로 올린다. 공통 원칙의 기준 버전은 백엔드 constitution 버전을 따른다.
- **준수 점검**: `/speckit-plan`의 Constitution Check와 PR 리뷰에서 원칙 준수를 확인한다. 위반이 불가피하면 plan의 Complexity Tracking에 사유를 적고 리뷰어 승인을 받는다.
