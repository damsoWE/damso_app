## User Scenarios & Testing *(mandatory)*

### User Story 1 - 배포 서버 계정으로 가입·로그인하고 로그인 상태가 유지된다 (Priority: P1)

학교 관리자·교사·학부모가 앱을 배포 서버에 연결된 상태로 실행해 가입하고 로그인한다. 앱을 껐다 켜도 로그인 상태가 유지되고, 로그인 유효 시간이 지나도 사용자가 다시 로그인하지 않고 계속 쓸 수 있다. 로그아웃하면 로그인 화면으로 돌아간다.

**Why this priority**: 로그인이 안 되면 나머지 모든 화면을 실서버로 확인할 수 없다. 실연동의 첫 관문이다.

**Independent Test**: 배포 서버로 실행한 앱에서 역할별 계정 하나씩으로 로그인 → 앱 재시작 → 홈이 바로 보이는지, 로그아웃 → 로그인 화면으로 가는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 배포 서버에 연결된 앱, **When** 학부모가 초대 코드로 가입을 마치면, **Then** 학부모 홈이 서버에 저장된 자녀·학급 정보로 표시된다.
2. **Given** 로그인한 사용자, **When** 앱을 완전히 종료했다가 다시 열면, **Then** 로그인 화면 없이 역할에 맞는 홈이 열린다.
3. **Given** 로그인 유효 시간이 지난 상태, **When** 사용자가 화면을 조작하면, **Then** 다시 로그인하라는 화면 없이 요청이 성공한다.
4. **Given** 로그인 연장마저 실패한 상태(예: 서버에서 세션이 끊김), **When** 사용자가 화면을 조작하면, **Then** 로그인 화면으로 이동한다.
5. **Given** 잘못된 이메일·비밀번호, **When** 로그인하면, **Then** 서버가 준 안내 문구만 보인다.

### User Story 2 - 학부모가 보낸 문의가 교사에게 실제로 도착한다 (Priority: P1)

학부모가 문의를 보내면 같은 학급의 교사 앱 문의 목록에 나타난다. 긴급으로 분류된 문의는 교사에게 긴급으로 표시된다. 학부모는 자기 문의의 처리 단계를 본다.

**Why this priority**: 학부모 → 교사 전달이 이 앱의 핵심 가치다. 두 기기(또는 두 계정) 사이에서 실제로 오가는지 처음 확인하는 지점이다.

**Independent Test**: 같은 학급의 학부모·교사 계정으로 학부모가 일반 문의 1건·긴급 문의 1건을 보내고, 교사 목록에 두 건이 맞는 표시로 보이는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 같은 학급에 연결된 학부모·교사, **When** 학부모가 일반 문의를 보내면, **Then** 교사가 목록을 새로 고쳤을 때 그 문의가 보인다.
2. **Given** 같은 조건, **When** 학부모가 긴급 표현이 들어간 문의를 보내면, **Then** 교사 목록에서 긴급으로 표시된다.
3. **Given** 문의를 보낸 학부모, **When** 문의 상세를 열면, **Then** 서버가 정한 현재 처리 단계가 보인다.
4. **Given** 다른 학부모의 문의 식별자, **When** 그 문의에 접근하면, **Then** 내용이 보이지 않고 서버의 접근 거부 안내만 보인다.

---

### User Story 3 - 교사가 서버가 정리한 결과를 본다 (Priority: P2)

교사가 일반 문의를 열면 서버가 정리한 "번역본"이 보인다. 정리가 진행 중이면 진행 중 화면이, 정리에 실패했으면 "원문 확인 필요" 화면이 보인다. 교사는 다시 정리하기와 원문 열람을 실제로 할 수 있다.

**Why this priority**: F3 화면은 정리 상태가 시간에 따라 바뀌는데, mock은 이 변화를 흉내만 냈다. 실제 처리 시간과 상태 변화로 확인해야 하지만, 로그인·문의 전달(P1)이 먼저 되어야 확인할 수 있다.

**Independent Test**: 교사 계정으로 정리가 끝난 문의 1건, 정리 중인 문의 1건을 열어 각 화면이 맞게 나오고, "다시 확인"으로 정리 중 → 완료 전환을 확인한다.

**Acceptance Scenarios**:

1. **Given** 정리가 끝난 일반 문의, **When** 교사가 상세를 열면, **Then** 번역본(사실관계·요청사항·정서강도)이 보인다.
2. **Given** 정리 중인 문의, **When** 교사가 "다시 확인"하거나 당겨서 새로 고치면, **Then** 정리가 끝난 경우 번역본으로 바뀐다.
3. **Given** "원문 확인 필요" 문의, **When** 교사가 상세를 열면, **Then** 정리본은 보이지 않고 안내·원문 열람·다시 정리하기만 보인다.
4. **Given** 이미 다시 정리하기를 1회 쓴 문의, **When** 교사가 다시 시도하면, **Then** 서버가 준 안내 문구가 보이고 버튼이 다시 나타나지 않는다.

---

### User Story 4 - 관리자가 학급·학생·초대 코드를 실제로 운영한다 (Priority: P2)

학교 관리자가 학급을 만들고 학생을 등록하고 초대 코드를 발급·재발급한다. 발급한 코드로 교사·학부모가 실제로 가입할 수 있다. 모든 역할이 내 정보·회원 탈퇴 화면을 쓸 수 있다.

**Why this priority**: US1·US2를 확인하려면 학급과 초대 코드가 있어야 한다. 테스트 데이터를 앱에서 직접 만들 수 있게 하는 경로다.

**Independent Test**: 관리자 계정으로 학급 1개 생성 → 학생 등록 → 교사·학부모 초대 코드 발급 → 그 코드로 새 계정 가입 성공을 확인한다.

**Acceptance Scenarios**:

1. **Given** 관리자 로그인, **When** 학급을 만들고 학생을 등록하면, **Then** 학급 상세에 서버에 저장된 학생 목록이 보인다.
2. **Given** 발급된 초대 코드, **When** 교사·학부모가 그 코드로 가입하면, **Then** 해당 학급에 연결된다.
3. **Given** 초대 코드 재발급, **When** 이전 코드로 가입을 시도하면, **Then** 서버의 거부 안내가 보인다.

---

### User Story 5 - 서버에 닿지 못하거나 서버가 거부해도 앱이 멈추지 않는다 (Priority: P2)

네트워크가 끊기거나 서버가 응답하지 않거나 서버가 오류를 돌려주면, 사용자는 이해할 수 있는 안내와 다시 시도할 방법을 본다. 오류의 내부 내용은 보이지 않는다.

**Why this priority**: mock은 네트워크 실패가 없었다. 실서버에서는 처음 생기는 상황이라 앱이 빈 화면·무한 로딩에 빠지지 않는지 확인해야 한다.

**Independent Test**: 비행기 모드에서 로그인·목록 조회를 시도하고, 연결을 되살린 뒤 다시 시도로 회복되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 네트워크 끊김, **When** 사용자가 목록을 열면, **Then** 연결 실패 안내와 다시 시도 버튼이 보이고 로딩이 끝없이 이어지지 않는다.
2. **Given** 서버가 오류를 돌려줌, **When** 화면이 그 응답을 받으면, **Then** 서버가 준 안내 문구만 보이고 예외 내용·내부 코드는 보이지 않는다.
3. **Given** 입력값 오류(예: 가입 양식), **When** 서버가 항목별 오류를 돌려주면, **Then** 해당 입력란 아래에 표시된다.

### User Story 6 - 개발자가 서버 없이도 계속 실행할 수 있다 (Priority: P3)

개발자·리뷰어는 실서버 대신 mock으로 앱을 실행하는 방법을 계속 쓸 수 있다. 실행 설정만 바꿔 배포 서버·로컬 서버·mock 중 하나를 고른다.

**Why this priority**: 서버 장애나 데이터 오염 없이 화면을 확인하는 수단을 잃으면 안 된다. 다만 기존 기능이 이미 지원하므로 회귀만 막으면 된다.

**Independent Test**: 같은 코드로 mock 설정, 배포 서버 설정 각각으로 실행해 둘 다 로그인 화면까지 뜨는지 확인한다.

**Acceptance Scenarios**:

1. **Given** mock 실행 설정, **When** 앱을 실행하면, **Then** 서버 없이 기존 mock 시나리오(토큰 만료, 남의 문의, 정리 중 → 완료, 원문 확인 필요, 긴급 문의)가 그대로 동작한다.
2. **Given** 배포 서버 실행 설정, **When** 앱을 실행하면, **Then** 모든 요청이 https://damso.jibang.site 로 간다.

### Edge Cases

- 서버 응답에 앱이 모르는 처리 단계·상태 값이 오면: 화면이 깨지지 않고 알 수 없는 상태로 표시된다.
- 서버 응답에 앱이 기대한 항목이 빠져 있으면: 해당 화면에 오류 안내가 보이고 앱이 종료되지 않는다.
- 응답이 오래 걸리면(예: 느린 네트워크): 일정 시간 뒤 시간 초과 안내와 다시 시도가 보인다.
- 로그인 연장 요청이 동시에 여러 개 생기면: 사용자는 한 번도 로그인 화면으로 튕기지 않는다.
- 다른 기기에서 탈퇴·로그아웃한 계정으로 앱을 열면: 로그인 화면으로 이동한다.
- 배포 서버의 API 버전이 앱 사본과 다르면: 어긋난 항목 목록을 만들고 이 기능 안에서 고친다(F4 신규 경로는 제외).
- 배포 서버에 쌓인 테스트 데이터: 실제 학생 이름·실명 문의를 넣지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 앱은 실행 설정만으로 배포 서버(https://damso.jibang.site)에 연결해 실행할 수 있어야 한다. 화면 코드를 바꾸지 않는다.
- **FR-002**: 앱은 실행 설정만으로 mock 실행·로컬 서버 실행을 계속 지원해야 한다. mock 구현과 mock 시나리오를 지우지 않는다.
- **FR-003**: 앱이 가진 API 계약 사본은 배포 서버가 쓰는 태그와 일치해야 한다. 사본은 직접 고치지 않고 백엔드 태그에서 받아 온다.
- **FR-004**: F1(가입·로그인·로그인 유지·로그인 연장·로그아웃·비밀번호 재설정·자녀 추가·학급 연결·내 정보·탈퇴) 화면은 배포 서버에서 수용 시나리오대로 동작해야 한다.
- **FR-005**: 관리자 화면(학급 생성·학생 등록·초대 코드 발급·재발급)은 배포 서버에서 동작해야 한다.
- **FR-006**: F2(학부모 문의 접수·처리 단계 표시, 교사 문의 목록·긴급 표시) 화면은 배포 서버에서 동작해야 한다.
- **FR-007**: F3(번역본 상세, 정리 중, 원문 확인 필요, 다시 정리하기, 원문 열람) 화면은 배포 서버에서 동작해야 한다.
- **FR-008**: 서버 응답 형식이 앱이 기대한 형식과 다르면, 앱을 서버 계약에 맞춘다. 서버 쪽 문제로 판단되면 백엔드에 이슈로 알리고 앱에서 임시로 우회하지 않는다.
- **FR-009**: 네트워크 끊김·시간 초과·서버 오류 시 화면은 안내와 다시 시도 수단을 보여 줘야 하며, 무한 로딩·빈 화면·앱 종료가 생기면 안 된다.
- **FR-010**: 사용자에게 보이는 오류 문구는 서버가 준 안내 문구 또는 앱의 고정 안내 문구뿐이어야 한다. 예외 내용·내부 코드·스택트레이스를 보여 주지 않는다.
- **FR-011**: 실서버 연동 중에도 문의·답변 본문, 로그인 정보를 기기 로그·분석 이벤트로 내보내지 않는다.
- **FR-012**: 실행 설정 파일에는 서버 주소 같은 공개 값만 둔다. 계정 비밀번호·키·토큰을 저장소에 넣지 않는다.
- **FR-013**: 배포 서버 기준 확인 결과(기능별 성공·실패, 발견한 계약 불일치와 처리 방법)를 기록으로 남긴다.
- **FR-014**: 푸시 알림 실연동이 빠진 상태에서도 앱은 정상 동작해야 한다. 알림 설정이 없어 기기 등록이 실패해도 로그인·목록·상세 화면에 오류가 보이거나 흐름이 막히지 않는다.

### Key Entities

- **실행 환경**: 앱이 연결할 대상(배포 서버·로컬 서버·mock)과 서버 주소. 공개 값만 가진다.
- **API 계약 사본**: 앱이 따르는 서버 API 명세의 복사본. 백엔드 태그(현재 `api-v0.4`, 최신 `api-v0.6`) 하나에 고정된다.
- **계약 불일치 기록**: 실연동 중 발견한 서버 응답과 앱 기대의 차이. 화면, 항목, 처리 방법(앱 수정/백엔드 이슈)을 담는다.
- **테스트 계정**: 역할(관리자·교사·학부모)별 배포 서버 계정. 저장소 밖에서만 공유한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: F1~F3 수용 시나리오(US1~US5) 전부가 배포 서버에서 통과한다(통과율 100%, 결과 기록 있음).
- **SC-002**: 학부모가 문의를 보낸 뒤 교사가 목록을 새로 고치면 1회 안에 그 문의가 보인다.
- **SC-003**: 앱을 재시작한 사용자 10명 중 10명이 다시 로그인하지 않고 홈에 들어간다.
- **SC-004**: 네트워크 끊김 상태에서 어떤 화면도 15초 넘게 로딩 표시에 머물지 않는다.
- **SC-005**: 사용자에게 보인 오류 문구 중 예외 내용·내부 코드가 섞인 것이 0건이다.
- **SC-006**: mock 실행으로 기존 자동 테스트가 전부 통과한다(회귀 0건).

## Assumptions

- 배포 서버는 백엔드 최신 API 태그(`api-v0.6`)를 반영하고 있다고 가정한다. 실제 태그는 계획 단계에서 백엔드에 확인한다.
- 배포 서버의 API 문서 화면은 인증이 걸려 있어(응답 401) 앱 개발자가 직접 볼 수 없다. 계약 확인은 백엔드 저장소의 태그 사본으로 한다.
- 역할별 테스트 계정(특히 첫 관리자 계정)은 백엔드 팀이 저장소 밖 경로로 제공한다. 서버는 기본 계정을 두지 않는다(원칙 VIII).
- 가입 시 이메일 인증이 필요하면 배포 서버가 실제 메일을 보낸다고 가정한다. 안 되면 백엔드에 확인한다.
- 서버 주소는 https라 기기의 평문 통신 허용 설정은 필요 없다.
- F4(답변 작성·점검·전송, 추가 문의, 문의 종료)와 학부모 알림 설정 화면은 범위 밖이다. v0.6 사본에 경로가 생겨도 이 기능에서 화면을 만들지 않는다.
- 푸시 알림 실연동(기기 등록·알림 수신·알림 눌러 이동)은 범위 밖이다. 별도 이슈로 진행한다(Clarifications 2026-10-28).
- 스토어 배포·릴리스 빌드 배포는 범위 밖이다.
- 테스트 데이터에는 가상의 이름·문장만 쓴다.
