## User Scenarios & Testing *(mandatory)*

### User Story 1 - 교사가 정리된 "번역본"을 본다 (Priority: P1)

교사가 문의 목록(F3-1)이나 홈(F3-4)에서 정리가 끝난 일반 문의를 누르면 정리본 상세(F3-2)가 열린다. "번역본"으로 사실관계·요청사항·정서강도(낮음·보통·높음 + 감정 라벨 최대 2개)가 보이고, 이름·학급은 원래 값으로 되돌려져 있다. 처음 연 순간 학부모 쪽 처리 단계가 "교사 확인"으로 바뀐다(서버가 정한다).

**Why this priority**: 감정이 실린 문의를 정리해 교사의 부담을 줄이는 것이 이 기능의 핵심 가치다. 번역본이 보이지 않으면 F3의 의미가 없다.

**Independent Test**: mock 실행에서 교사로 로그인해 정리 완료 문의를 열고, 사실관계·요청사항·정서강도·라벨이 보이는지, 목록으로 돌아왔을 때 그 문의의 단계가 "교사 확인"으로 바뀌어 보이는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 정리가 끝난 일반 문의, **When** 교사가 목록에서 누름, **Then** 정리본 상세(F3-2)가 열리고 "번역본" 표시와 함께 사실관계·요청사항·정서강도가 보인다.
2. **Given** 정서강도가 "높음"이고 라벨이 "분노·답답함"인 번역본, **When** 상세를 봄, **Then** 정서강도 3단계 중 "높음"이 구분되어 보이고 라벨 두 개가 보인다.
3. **Given** 요청사항이 없는 번역본(서버가 빈 값으로 줌), **When** 상세를 봄, **Then** 요청사항 영역에 "요청사항이 없어요" 같은 고정 문구가 보이고 빈 칸으로 남지 않는다.
4. **Given** 감정 라벨이 없는 번역본, **When** 상세를 봄, **Then** 정서강도만 보이고 라벨 영역은 비어 보이지 않게 숨겨진다.
5. **Given** 정리본 상세를 처음 연 뒤, **When** 문의 목록으로 돌아옴, **Then** 그 문의의 처리 단계가 "교사 확인"으로 바뀌어 보인다.
6. **Given** 정리본 상세, **When** 화면의 모든 글자를 점검, **Then** 학부모의 이름·이메일·연락처는 없고 학생 이름으로 구분된다.
7. **Given** 다른 학급의 문의 주소로 직접 이동, **When** 서버가 거부, **Then** 서버 안내가 보이고 내용은 보이지 않는다.

### User Story 2 - 정리에 실패한 문의는 실패 안내와 원문 확인·다시 정리하기를 보여 준다 (Priority: P1)

자동 정리가 두 번 실패하면 문의는 "원문 확인 필요"가 된다. 교사가 그 문의를 열면 원문 확인 필요(F3-3) 화면이 열리고, "자동 정리에 실패했습니다. 원문을 확인해 주세요" 안내, 원문 보기 버튼, 다시 정리하기 버튼(문의 1건당 1회)이 보인다. 정리되지 않은 결과는 어떤 경우에도 보이지 않는다. 다시 정리하기를 누르면 다시 정리하는 중(F3-3a)으로 바뀌고, 성공하면 번역본을, 또 실패하면 원문 확인만 할 수 있는 화면을 본다.

**Why this priority**: 잘못 정리된 글이 사실처럼 보이는 것을 막는 안전장치다(원칙 IV). 실패 상태에서도 교사가 문의 내용을 확인할 길이 있어야 문의가 묻히지 않는다.

**Independent Test**: mock 실행에서 "원문 확인 필요" 문의를 열어 안내·두 버튼을 확인하고, 다시 정리하기가 성공하는 문의와 실패하는 문의 각각에서 결과 화면과 버튼 상태를 확인한다.

**Acceptance Scenarios**:

1. **Given** "원문 확인 필요" 문의(재시도 가능), **When** 교사가 목록에서 누름, **Then** F3-3이 열리고 "자동 정리에 실패했습니다. 원문을 확인해 주세요" 안내, 원문 보기 버튼, 다시 정리하기 버튼이 보인다. 정리 결과는 보이지 않는다.
2. **Given** F3-3, **When** 다시 정리하기를 누름, **Then** 버튼이 바로 진행 중 상태가 되어 다시 누를 수 없고, 서버가 받아들이면 다시 정리하는 중(F3-3a)이 보인다. 이 화면에서도 원문 보기와 문의 목록으로 가기는 쓸 수 있다.
3. **Given** 다시 정리하기가 성공함, **When** 교사가 결과를 확인함(확인 방식은 FR-012), **Then** 정리본 상세(F3-2)와 같은 번역본이 보인다.
4. **Given** 다시 정리하기도 실패함, **When** 교사가 다시 상세를 엶, **Then** 실패 안내와 원문 보기 버튼만 보이고 다시 정리하기 버튼은 없다. "다시 정리하기는 한 번만 할 수 있다"는 안내가 함께 보인다.
5. **Given** 이미 다시 정리하기를 쓴 문의, **When** 목록에서 누름, **Then** 다시 정리하기 버튼이 보이지 않는다.
6. **Given** 다시 정리하기를 눌렀는데 서버가 거부(이미 사용함·동시 요청 등), **When** 응답을 받음, **Then** 서버 안내가 보이고 화면은 서버의 최신 상태로 다시 그려진다.
7. **Given** 다시 정리하기 요청이 네트워크 오류로 실패, **When** 실패 안내가 보임, **Then** 버튼은 다시 누를 수 있는 상태로 돌아온다(서버가 받아들이지 않았으므로 1회가 소모되지 않는다).

### User Story 3 - 교사가 원문을 열람하고, 열람이 기록된다는 것을 안다 (Priority: P1)

교사는 정리본 상세·원문 확인 필요·다시 정리하는 중 화면에서 "원문 보기"를 눌러 원문 열람(F3-6)을 연다. 원문 보기 버튼 가까이와 원문 화면에 열람 기록 안내(data-model 고정 문구)가 보인다. 원문은 학부모가 쓴 그대로 일반 글자로 보인다.

**Why this priority**: 정리본이 원문을 가리는 "검열"이 아님을 보장하는 장치다(원칙 III). "원문 확인 필요" 상태에서는 원문이 교사가 내용을 볼 유일한 길이다.

**Independent Test**: mock 실행에서 세 상태(정리 완료·정리 중·원문 확인 필요)의 문의에서 원문을 열어 원문이 보이는지, 열람 안내가 버튼 근처와 원문 화면 모두에 보이는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 정리본 상세, **When** 원문 보기를 누름, **Then** 원문 열람(F3-6)이 열리고 원문이 그대로 보이며 열람 기록 안내(data-model 고정 문구)가 보인다.
2. **Given** 원문 보기 버튼, **When** 누르기 전, **Then** 버튼 근처에 열람이 기록된다는 안내가 보인다.
3. **Given** "원문 확인 필요" 문의, **When** 원문을 처음 열람한 뒤 목록으로 돌아옴, **Then** 그 문의의 처리 단계가 "교사 확인"으로 바뀌어 보인다(서버가 정한다).
4. **Given** 원문 열람이 서버에서 거부되거나 실패함, **When** 응답을 받음, **Then** 서버 안내가 보이고 원문은 보이지 않는다. 다시 시도할 수 있다.
5. **Given** 원문 열람 화면, **When** 화면을 떠남, **Then** 원문은 기기에 남지 않는다. 다시 보려면 다시 열람해야 하고 그때마다 기록이 남는다.
6. **Given** 원문 열람 화면, **When** "문의 상세로"를 누름, **Then** 그 문의의 상세(F3-2·F3-3·F3-3a 중 현재 상태에 맞는 화면)로 돌아간다.

### User Story 4 - 정리 중인 문의도 열 수 있고, 정리가 끝나면 번역본으로 바뀐다 (Priority: P2)

정리 확정 뒤에 알림이 가므로 대부분 교사는 정리된 문의를 연다. 그래도 목록에는 정리 중인 문의가 "정리 중" 제목으로 보일 수 있고, 교사가 그것을 누르면 정리 중 안내와 원문 보기 버튼이 보인다. 정리가 끝나면 번역본으로 바뀐다.

**Why this priority**: 정리 확정 알림이 정상 흐름이라 드문 경우지만, 외부 AI가 느릴 때 교사가 빈 화면이나 "준비 중"을 보지 않게 해야 한다.

**Independent Test**: mock 실행에서 "정리 중" 문의를 열어 정리 중 안내와 원문 보기가 보이는지, 정리가 끝난 뒤 번역본으로 바뀌는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 정리 중인 일반 문의, **When** 교사가 누름, **Then** "자동 정리 중이에요" 같은 고정 안내와 원문 보기 버튼이 보이고 정리 결과는 보이지 않는다.
2. **Given** 정리 중 화면에서 정리가 끝남, **When** 교사가 "다시 확인"을 누르거나 당겨서 새로 고침, **Then** 번역본(F3-2)이 보인다.
3. **Given** 정리 중 화면에서 정리가 실패로 확정됨, **When** 교사가 "다시 확인"을 누름, **Then** 원문 확인 필요(F3-3)가 보인다.
4. **Given** 정리 중 화면, **When** 아무 동작도 하지 않음, **Then** 화면은 저절로 바뀌지 않고 "정리가 끝나면 다시 확인을 눌러 주세요" 안내가 보인다.

### User Story 5 - 학부모는 정리 결과 없이 처리 단계만 본다 (Priority: P2)

학부모는 나의 문의 목록(F2-4)의 카드에서 일반 문의가 접수 → 정제 → 교사 확인으로 진행되는 것을 시각과 함께 본다. 번역본·정서강도·감정 라벨·정리 실패 사실은 학부모에게 보이지 않는다.

**Why this priority**: 학부모 화면은 F2의 타임라인을 그대로 쓰므로 새로 만들 것이 적다. 다만 F3에서 처음으로 "정제"와 "교사 확인"이 실제로 쌓이므로 확인이 필요하다.

**Independent Test**: mock 실행에서 같은 일반 문의를 교사로 연 뒤 학부모로 바꿔 카드를 펼쳐 단계가 바뀌었는지, 정리 결과가 어디에도 없는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 정리가 끝난 일반 문의, **When** 학부모가 카드를 펼침, **Then** "접수" 다음에 "정제"가 시각과 함께 보인다.
2. **Given** 교사가 번역본을 처음 연 문의, **When** 학부모가 카드를 펼침, **Then** "교사 확인"이 시각과 함께 보인다.
3. **Given** "원문 확인 필요" 문의, **When** 학부모가 카드를 펼침, **Then** "정제"가 보이지 않고 실패했다는 사실이나 사유도 보이지 않는다. 교사가 원문을 열면 "접수" 다음에 "교사 확인"이 보인다.
4. **Given** 학부모 화면 전체, **When** 점검, **Then** 번역본·정서강도·감정 라벨이 보이는 곳이 없다.

---

### User Story 6 - 서버 없이 mock으로 정리의 모든 상태를 시연한다 (Priority: P2)

개발자와 기획자가 서버 없이 mock으로 실행해 정리 중 → 정리 완료, 원문 확인 필요(재시도 가능), 다시 정리하기 성공, 다시 정리하기 실패, 이미 재시도한 문의, 남의 문의 접근 거부(403), 번역본이 아직 없음(409), 재시도 거부(409), 접근 권한 만료 → 갱신을 모두 볼 수 있다.

**Why this priority**: constitution이 요구하는 mock 케이스("정제 진행 중 → 완료", "원문 확인 필요")이고, 외부 AI 결과에 따라 갈리는 상태라 실서버로는 원하는 상태를 재현하기 어렵다.

**Independent Test**: mock 실행에서 quickstart의 데모 문의표대로 각 상태를 재현한다.

**Acceptance Scenarios**:

1. **Given** mock 실행, **When** 교사 문의 목록을 엶, **Then** 정리 완료·정리 중·원문 확인 필요(재시도 가능)·원문 확인 필요(재시도 사용함) 데모 문의가 각각 있다.
2. **Given** mock 실행, **When** 정해 둔 데모 문의에서 다시 정리하기를 누름, **Then** 성공하는 문의와 실패하는 문의를 각각 재현할 수 있다.
3. **Given** mock 실행, **When** 남의 문의를 여는 데모 동작, **Then** 403 서버 안내가 보인다.

### Edge Cases

- 목록에서는 "정리 완료"였는데 상세를 열 때 서버가 번역본이 아직 없다고 거부하면(409), 서버 안내를 보이고 문의 상세 상태를 다시 불러와 그 상태에 맞는 화면을 보인다.
- 앱이 모르는 정서강도 값이 오면 정서강도 영역을 숨기고 사실관계·요청사항은 그대로 보인다. 앱이 모르는 감정 라벨은 버리고 아는 라벨만 보인다. 서버 형식을 벗어난 값을 추측해서 보여 주지 않는다.
- 번역본 글은 일반 글자로만 보인다. 링크·서식으로 해석하지 않는다(원칙: WebView·HTML 렌더 금지).
- 번역본·원문은 화면이 열려 있는 동안 메모리에만 있고 기기 저장소·로그·분석 이벤트·크래시 리포트에 남기지 않는다(원칙 III·VI).
- 정리 상태가 서버에서 바뀌는 동안(정리 중 → 완료) 교사가 이미 열어 둔 상세는 FR-012의 규칙으로만 바뀐다. 목록은 F2의 다시 불러오기 규칙(화면 열 때·탭 복귀·당겨서 새로 고침·알림 수신·앱 복귀)을 따른다.
- 다시 정리하기 성공 시 교사에게 추가 알림은 오지 않는다(서버 규칙). 교사는 "다시 확인"·당겨서 새로 고침으로 결과를 확인한다(FR-012).
- 다시 정리하는 중(F3-3a)에서 화면을 떠났다가 다시 오면 서버의 현재 상태로 화면을 고른다(정리 중이면 F3-3a, 성공이면 F3-2, 실패면 재시도 버튼 없는 F3-3).
- 긴급 문의는 정리 대상이 아니다. 긴급 문의를 누르면 지금처럼 긴급 문의 상세(F3-5)가 열리고, F3 화면은 열리지 않는다.
- 학부모 계정·슈퍼 관리자가 F3 화면 주소로 들어오면 자기 역할 홈으로 보낸다(F2와 같은 접근 규칙).
- 일반 문의 알림이 정리 확정 시점에 오므로, 교사가 알림을 눌러 열었을 때는 번역본이나 실패 안내가 보이는 것이 정상이다. 알림을 누르면 F2와 같이 문의 목록(F3-1)으로 간다.

## Requirements *(mandatory)*

### Functional Requirements

**화면 고르기 (교사)**

- **FR-001**: 교사가 문의 목록(F3-1)·교사 홈(F3-4)에서 일반 문의를 누르면 서버가 준 정리 상태에 맞는 화면을 연다. 정리 완료 → 정리본 상세(F3-2), 원문 확인 필요 → F3-3, 정리 중 → 정리 중 안내 화면(US4). 긴급 문의는 지금처럼 긴급 문의 상세(F3-5)를 연다.
- **FR-002**: F2가 일반 문의에 보여 주던 "준비 중" 화면과 문구는 이 기능의 화면으로 대체하고 남기지 않는다.
- **FR-003**: 상세를 열 때 서버의 최신 문의 상태를 먼저 불러와 화면을 고른다. 목록의 상태와 다르면 서버의 최신 상태를 따른다.

**정리본 상세 (F3-2)**

- **FR-004**: 정리본 상세는 학생 이름·접수 시각·현재 처리 단계와 함께 "번역본" 표시, 사실관계, 요청사항, 정서강도(낮음·보통·높음 중 하나), 감정 라벨(불안·불만·분노·걱정·답답함·슬픔 중 최대 2개)을 보여 준다.
- **FR-005**: 정서강도·감정 라벨의 표시 문구는 앱에 정해 둔 고정 문구로 바꿔 보여 준다. 앱이 모르는 값은 FR-005a에 따른다.
- **FR-005a**: 앱이 모르는 정서강도 값이면 정서강도 영역을 숨기고, 앱이 모르는 감정 라벨은 버린다. 라벨이 하나도 남지 않으면 라벨 영역을 숨긴다.
- **FR-006**: 요청사항이 빈 값이면 고정 문구("요청사항이 없어요")를 보여 준다.
- **FR-007**: 번역본·원문은 일반 글자로만 표시하고, 링크·서식으로 해석하지 MUST NOT 한다.
- **FR-008**: 정리본 상세에는 원문 보기 버튼과 열람 기록 안내(data-model 고정 문구)를 함께 둔다.
- **FR-009**: 번역본을 보여 주기 위해 서버에 요청하는 것 자체로 처리 단계가 "교사 확인"으로 바뀔 수 있다(서버가 정한다). 앱은 번역본을 불러온 뒤 문의 목록·교사 홈이 다시 보일 때 바뀐 단계를 반영한다.

**원문 확인 필요 (F3-3) · 다시 정리하는 중 (F3-3a)**

- **FR-010**: 원문 확인 필요 화면은 고정 문구 "자동 정리에 실패했습니다. 원문을 확인해 주세요"와 원문 보기 버튼을 보여 주고, 서버가 재시도 가능하다고 알려 준 경우에만 다시 정리하기 버튼을 보여 준다. 정리 결과는 어떤 형태로도 보여 주지 MUST NOT 한다.
- **FR-011**: 다시 정리하기를 누르면 요청이 끝날 때까지 버튼을 다시 누를 수 없다. 서버가 받아들이면 다시 정리하는 중(F3-3a) 상태를 보인다. 서버가 거부하면 서버 안내를 보이고 문의 상태를 다시 불러와 화면을 고친다. 네트워크 오류면 실패 안내를 보이고 버튼을 다시 누를 수 있게 둔다.
- **FR-012**: 정리 중(US4)·다시 정리하는 중(F3-3a) 화면은 교사가 "다시 확인" 버튼을 누르거나 당겨서 새로 고칠 때 서버의 정리 상태를 다시 불러오고, 바뀌었으면 그 상태에 맞는 화면(정리 완료 → F3-2, 원문 확인 필요 → F3-3)으로 바꾼다. 일정 간격으로 자동 조회하지 않는다(F2와 같은 규칙). 화면에는 "정리가 끝나면 다시 확인을 눌러 주세요" 같은 고정 안내를 함께 보인다. 다시 확인하는 동안에도 보던 화면은 그대로 둔다.
- **FR-013**: 다시 정리하는 중 화면에서도 원문 보기와 "문의 목록으로"를 쓸 수 있다.
- **FR-014**: 재시도를 이미 쓴 "원문 확인 필요" 문의는 다시 정리하기 버튼 없이 실패 안내와 원문 보기, "다시 정리하기는 한 번만 할 수 있어요" 고정 안내를 보여 준다.

**원문 열람 (F3-6)**

- **FR-015**: 원문 보기 버튼은 정리본 상세·원문 확인 필요·다시 정리하는 중·정리 중 화면에 모두 둔다. 누르면 원문 열람(F3-6)이 열리고 원문과 열람 기록 안내(data-model 고정 문구)가 보인다.
- **FR-016**: 원문 열람은 화면을 열 때마다 서버에 요청한다. 원문을 기기 저장소에 저장하거나 화면 밖에 남기지 MUST NOT 한다. 이전에 받은 원문을 다시 보여 주는 방식으로 열람 요청을 건너뛰지 않는다.
- **FR-017**: 원문 열람이 거부되거나 실패하면 서버 안내만 보이고 원문은 보이지 않는다. 다시 시도 버튼을 둔다.
- **FR-018**: 원문 열람 화면의 "문의 상세로"는 그 문의의 현재 상태에 맞는 상세 화면으로 돌아간다.

**공통 (교사)**

- **FR-019**: F3 화면 어디에도 학부모의 이름·이메일·연락처를 보여 주지 MUST NOT 한다. 문의는 학생 이름으로 구분한다.
- **FR-020**: 화면 안내 문구(번역본 표시, 실패 안내, 정리 중 안내, 재시도 한도 안내, 열람 기록 안내, 요청사항 없음)는 모두 앱에 정해 둔 고정 문구다. 서버 오류 안내(`message`)만 서버 문장을 그대로 쓴다.
- **FR-021**: F3 화면은 교사만 들어갈 수 있다. 다른 역할이 주소로 들어오면 자기 역할 홈으로 보낸다. 다른 학급 문의처럼 서버가 거부하면 서버 안내만 보이고 내용은 보이지 않는다.
- **FR-022**: 각 화면은 로딩·오류(서버 `message`, 다시 시도) 상태를 갖는다. 서버 오류는 F1·F2와 같은 규칙으로 보여 준다.
- **FR-023**: 답변 작성(F4-2a)으로 가는 버튼은 이 기능에서 두지 않는다. F4가 F3-2·F3-3·F3-6에 진입점을 더한다.

**학부모**

- **FR-024**: 학부모 화면은 F2의 처리 단계 타임라인을 그대로 쓰고, 서버가 준 단계(접수·정제·교사 확인)만 보여 준다. 번역본·정서강도·감정 라벨·정리 실패 사실을 보여 주는 화면 요소를 두지 MUST NOT 한다.

**mock**

- **FR-025**: mock 구현은 정리 중 → 정리 완료 전이, 원문 확인 필요(재시도 가능), 다시 정리하기 성공, 다시 정리하기 실패, 재시도를 이미 쓴 문의, 번역본 아직 없음(409), 재시도 거부(409), 남의 문의 접근 403, 접근 권한 만료 → 갱신 → 재시도를 재현해야 MUST 한다. 정리본 상세를 처음 열면 처리 단계가 "교사 확인"이 되고, "원문 확인 필요" 문의는 원문을 처음 열면 "교사 확인"이 되는 서버 규칙도 따라 한다.

### Key Entities *(include if feature involves data)*

- **번역본(화면 표시용)**: 문의 ID, 제목, 사실관계, 요청사항(없으면 빈 값), 정서강도(3단계), 감정 라벨(최대 2개), 정리 시각. 서버가 이름·학급을 원래 값으로 되돌려 준다. 화면이 열려 있는 동안 메모리에만 있다.
- **교사 문의 상세(확장)**: F2의 상세에 정리 상태(정리 중·정리 완료·원문 확인 필요, 긴급은 없음)와 재시도 가능 여부가 더해진다. 본문·번역본은 들어 있지 않고 따로 연다.
- **원문**: 문의 ID와 본문. 열람할 때마다 서버에 요청하며 기기에 남기지 않는다.
- **다시 정리하기 요청 결과**: 서버가 받아들였는지와 그 시점의 정리 상태. 결과는 상세의 정리 상태로 확인한다.
- **고정 안내 문구**: 번역본 표시, 정서강도·감정 라벨 이름, 정리 중 안내(다시 확인 안내 포함), 자동 정리 실패 안내, 재시도 한도 안내, 열람 기록 안내, 요청사항 없음.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 교사가 목록에서 정리 완료 문의를 누른 뒤 번역본을 보기까지 일반적인 네트워크에서 3초 안에 끝난다.
- **SC-002**: "원문 확인 필요"·정리 중 상태에서 정리 결과가 보이는 경우가 0건이다.
- **SC-003**: 다시 정리하기를 한 문의에서 두 번 이상 요청할 수 있는 화면 상태가 0개다(서버가 받아들인 뒤 버튼이 다시 나타나는 경우 0건).
- **SC-004**: 원문을 보여 주는 모든 화면(F3-6)과 원문 보기 버튼 근처에 열람 기록 안내가 보이는 비율이 100%다.
- **SC-005**: 원문·번역본이 기기 저장소·로그·분석 이벤트에서 발견되는 경우가 0건이다.
- **SC-006**: F3 화면에서 학부모의 이름·이메일·연락처가 보이는 경우가 0건이다.
- **SC-007**: 학부모 화면에서 번역본·정서강도·감정 라벨·정리 실패 사실이 보이는 경우가 0건이다.
- **SC-008**: 교사가 정리 상태와 관계없이 일반 문의를 눌러 "준비 중"이나 빈 화면을 보는 경우가 0건이다.
- **SC-009**: mock 실행만으로 US6의 모든 상태를 서버 없이 재현할 수 있다.

## Assumptions

- 로그인·역할별 하단 탭·교사 문의 목록·교사 홈·긴급 문의 상세(F3-5)·처리 단계 타임라인·기기 알림은 F1·F2에서 만든 것을 그대로 쓰고, 이 기능은 일반 문의를 누른 뒤의 화면을 채운다.
- 가명화·외부 AI 정리·형식 검증·자동 재시도·재시도 1회 한도·처리 단계 전이·원문 열람 기록·위기 종류 분류는 모두 서버가 한다. 앱은 판정 규칙을 갖지 않고 결과만 보여 준다.
- 위기 종류 분류(자해·학대·그 밖의 안전)는 백엔드 F3에서 채워지지만, 학부모 긴급 안내의 번호 고르기는 F2에서 이미 완성했으므로 이 기능에서 바꿀 화면은 없다. 실서버로 종류별 안내가 맞게 나오는지만 확인한다.
- 일반 문의 알림이 정리 확정 시점에 가도록 바뀐 것은 서버 변경이다. 알림을 누르면 F2처럼 문의 목록(F3-1)으로 간다(일반 알림은 묶여서 올 수 있다).
- API 명세 사본 `api-v0.4`에 정리 상태·재시도 가능 여부·번역본 열람·재시도·원문 열람이 이미 들어 있다. 백엔드가 새 태그를 공지하면 `/fetch-api`로 받아 차이를 plan에서 반영한다.
- 화면 배치와 정서강도 표시 모양(색·막대 등)은 Figma 프레임 F3-2·F3-3·F3-3a·F3-6(`docs/ia.md` 링크)을 따른다. 고정 문구는 Figma와 다르면 plan에서 하나로 맞춘다.
