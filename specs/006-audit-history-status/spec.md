## User Scenarios & Testing *(mandatory)*

### User Story 1 - 슈퍼 관리자가 학급별 문의 처리 현황을 건수로만 본다 (Priority: P1)

슈퍼 관리자(학교 관리자)는 "문의 현황" 화면에서 학급마다 문의가 몇 건 답변을 기다리는지, 교사가 확인했는지, 답변을 받았는지를 건수로 본다. 문의 제목·내용·학생 이름·학부모·교사 정보는 어디에도 보이지 않는다. 학급을 누르면 그 학급의 명단 화면(ADM-1)으로 간다.

**Why this priority**: F5에서 앱이 새로 보여 주는 유일한 화면이다. 학교가 응대 현황을 파악하는 수단이며, 민원 내용 없이 메타데이터만 다뤄야 한다는 원칙(원칙 VII)을 화면에서 지키는 곳이다.

**Independent Test**: mock 슈퍼 관리자 계정으로 문의 현황을 열어 학급마다 세 가지 건수가 mock 값과 같은지, 화면 어디에도 제목·본문·이름이 없는지, 문의가 없는 학급이 0으로 보이는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 슈퍼 관리자 로그인, **When** 문의 현황을 엶, **Then** 학급마다 학년·반과 "답변 대기 · 교사 확인 · 답변 완료" 건수가 보인다.
2. **Given** 문의 현황 화면, **When** 화면의 글자를 모두 살펴봄, **Then** 문의 제목·본문·학생 이름·학부모·교사 이름·이메일은 없다.
3. **Given** 문의가 하나도 없는 학급, **When** 현황을 엶, **Then** 그 학급도 세 건수가 0으로 보인다.
4. **Given** 학교 전체에 문의가 없음(모든 학급 0), **When** 현황을 엶, **Then** 학급 목록은 0으로 보이고 "아직 접수된 문의가 없어요" 안내가 함께 보인다.
5. **Given** 문의 현황 화면, **When** 학급을 누름, **Then** 그 학급의 상세(ADM-1)가 열린다.
6. **Given** 현황을 불러오는 중, **When** 응답을 기다림, **Then** 불러오는 중 표시가 보이고, 실패하면 서버가 준 문구와 다시 시도 버튼이 보인다.
7. **Given** 슈퍼 관리자가 아닌 계정(서버가 거부), **When** 현황을 요청, **Then** 내용 없이 서버의 권한 없음 문구만 보인다.
8. **Given** 접근 권한이 만료된 상태, **When** 현황을 엶, **Then** 자동으로 갱신해 다시 불러오고, 갱신이 거부되면 로그인 화면으로 간다.

### User Story 2 - 학부모·교사는 문의 상세에서 처리 단계만 본다 (Priority: P2)

학부모와 교사는 별도 이력 화면 없이 문의 상세의 처리 단계 타임라인(접수 → 정리 완료/긴급 전달 → 교사 확인)으로 진행을 확인한다. 서버가 남기는 감사 기록(누가 원문·번역본을 열었는지, 재시도·점검 요청 등)은 타임라인에 나오지 않는다.

**Why this priority**: F2가 타임라인을 이미 만들었다. 이 기능에서는 서버가 감사 기록을 넓혀도 타임라인에 섞이지 않는다는 것과, 앱 어디에도 감사 기록 화면이 없다는 것을 보장한다.

**Independent Test**: 원문 열람·재시도·점검 요청이 있었던 mock 문의를 학부모·교사 상세로 열어, 타임라인에 처리 단계와 시각만 있는지 확인한다. 앱의 모든 경로에 감사 기록 화면이 없는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 원문 열람·재시도 기록이 있는 문의, **When** 학부모가 상세를 엶, **Then** 타임라인에는 처리 단계와 시각만 있고 열람·재시도 항목은 없다.
2. **Given** 같은 문의, **When** 교사가 상세를 엶, **Then** 타임라인은 학부모와 같은 처리 단계 목록이다.
3. **Given** 서버가 앱이 모르는 처리 단계 값을 보냄, **When** 상세를 엶, **Then** 화면이 깨지지 않고 일반 오류 안내를 보인다(F2 규칙과 같다).
4. **Given** 학부모·교사·슈퍼 관리자 계정, **When** 앱의 모든 화면을 살펴봄, **Then** 감사 기록을 보거나 내보내는 화면은 없다.

---

### User Story 3 - 원문 열람이 기록 실패로 거부되면 원문 없이 안내만 본다 (Priority: P3)

교사가 원문을 열 때 서버가 열람 기록을 남기지 못하면 원문을 보내지 않는다(원칙 III). 이때 교사는 원문 대신 서버가 준 안내 문구와 다시 시도 버튼을 본다. 번역본·점검·재시도는 기록이 실패해도 서버가 정상 처리하므로 앱 동작이 바뀌지 않는다.

**Why this priority**: 서버가 이미 막아 주므로 앱이 새로 할 일은 거의 없다. 다만 원문이 일부라도 남아 보이거나 예외 내용이 보이면 안 되므로 확인한다.

**Independent Test**: mock에서 원문 열람 기록 실패를 재현해 원문 열람 화면(F3-6)과 긴급 상세(F3-5)가 원문 없이 서버 문구와 다시 시도만 보이는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 원문 열람 기록이 실패하는 상황, **When** 교사가 원문 보기를 누름, **Then** 원문은 보이지 않고 서버 문구와 다시 시도 버튼만 보인다.
2. **Given** 같은 상황, **When** 교사가 긴급 문의 상세를 엶, **Then** 원문 없이 화면에 서버 문구와 다시 시도 버튼만 보인다(긴급 상세는 원문을 먼저 받아야 그려지므로 화면 전체가 오류 안내다, research R6).
3. **Given** 위 상황 뒤 서버가 회복됨, **When** 다시 시도를 누름, **Then** 원문이 정상으로 보인다.

---

### Edge Cases

- **학급 이름을 모르는 현황 항목**: 현황에는 학급 식별자와 건수만 있다. 앱이 가진 학급 목록에 그 학급이 없으면(방금 만든 학급 등) 학년·반 대신 "학급"으로만 보이고, 건수는 그대로 보인다. 누르면 학급 상세로 간다.
- **현황과 학급 목록 중 하나만 실패**: 현황이 실패하면 화면 전체를 오류로 보인다. 학급 목록만 실패하면 건수는 보이고 학급 이름은 "학급"으로 보인다.
- **건수가 큼**: 세 자리 이상 건수도 잘리지 않고 보인다.
- **답변 뒤 재문의**: 답변을 보낸 스레드는 그 뒤 답하지 않은 재문의가 있어도 "답변 완료"로 센다(서버 기준, 교사 목록 `hasAnswer`와 같다). 앱은 서버 건수를 그대로 보이고 다시 계산하지 않는다.
- **긴급 문의**: 현황에서 긴급 여부는 드러나지 않는다(서버가 "답변 대기"에 합친다). 앱도 따로 표시하지 않는다.
- **슈퍼 관리자의 문의 내용 접근**: 현황에서 문의 목록·상세로 가는 이동은 없다.
- **세션 만료 중 현황**: 갱신 거부면 로그인 화면으로 가고, 다시 로그인하면 관리자 홈부터 시작한다.

## Requirements *(mandatory)*

### Functional Requirements

**슈퍼 관리자 문의 현황 (US1)**

- **FR-001**: 앱은 슈퍼 관리자에게 학급별 문의 처리 현황 화면(Figma ADM-4)을 제공해야 한다. 관리자 하단 탭의 "문의 현황"에서 연다.
- **FR-002**: 현황은 학급마다 학년·반과 세 건수를 보인다: "답변 대기"(교사 확인 전), "교사 확인"(확인했고 아직 답변 전), "답변 완료"(답변을 1건 이상 보냄). 건수는 서버 값을 그대로 쓰고 앱에서 처리 단계로 다시 나누지 않는다. 화면 위 요약(전체 문의·세 묶음 합계)은 학급별 서버 값을 더한 것이다(research R2).
- **FR-003**: 현황 화면에는 문의 제목·본문·정리 결과·답변·학생 이름·학부모·교사 이름·이메일·연락처를 보이지 않아야 한다(원칙 VII). 긴급 건수·학생별 건수도 보이지 않는다.
- **FR-004**: 문의가 없는 학급도 0으로 보인다. 모든 학급이 0이면 "아직 접수된 문의가 없어요" 안내를 함께 보인다. 학급이 하나도 없으면 학급 추가 안내를 보인다.
- **FR-005**: 학급 항목을 누르면 그 학급 상세(ADM-1)로 간다. 현황에서 문의 목록·문의 상세로 가는 이동은 없다.
- **FR-006**: 불러오는 중 표시, 오류(서버 `message`만, 다시 시도 버튼), 권한 없음(서버 문구) 상태를 보인다. 예외 객체·내부 오류 내용은 보이지 않는다.
- **FR-007**: 화면에 다시 들어오거나 당겨서 새로 고침하면 현황을 다시 불러온다.

**처리 단계 타임라인 (US2)**

- **FR-008**: 학부모·교사 문의 상세의 타임라인은 처리 단계(접수·긴급 전달·정리 완료·교사 확인)와 시각만 보여야 한다. 원문·번역본 열람, 재시도·점검 요청 같은 감사 항목은 보이지 않는다.
- **FR-009**: 앱 어디에도 감사 기록을 조회하거나 내보내는 화면·경로를 두지 않는다(감사 기록 조회는 서버 운영자 전용, 내보내기는 MVP 제외).

**원문 열람 기록 실패 (US3)**

- **FR-010**: 원문 열람(F3-6)·긴급 상세(F3-5)에서 서버가 원문을 거부하면, 원문을 일부라도 보이지 않고 서버 `message`와 다시 시도 버튼만 보인다. 이전에 받은 원문이 화면에 남아 있지 않아야 한다.

**mock (원칙: mock은 정상 경로만 두지 않는다)**

- **FR-011**: mock은 현황 정상(학급마다 다른 건수), 문의 없는 학급(0), 모든 학급 0, 403 권한 없음, 401 갱신 → 재시도 성공, 원문 열람 기록 실패를 재현해야 한다.

### Key Entities

- **학급별 문의 현황**: 학급 식별자, 답변 대기 건수, 교사 확인 건수, 답변 완료 건수. 서버가 조회할 때마다 만들어 주는 집계이며 앱은 화면이 열려 있는 동안만 가진다.
- **학급 표시 이름**: 학년·반. 관리자의 학급 목록에서 가져와 현황 항목과 학급 식별자로 맞춘다.
- **처리 단계 이력**: 문의가 어느 단계에 언제 들어섰는지(F2 그대로). 학부모·교사 타임라인의 원천.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 슈퍼 관리자가 문의 현황 탭을 누른 뒤 학급별 건수를 3초 안에 본다(보통 네트워크).
- **SC-002**: mock·실서버 모두에서 현황 화면의 건수가 서버 응답과 100% 일치한다.
- **SC-003**: 현황 화면과 타임라인 전체에서 문의 제목·본문·이름·이메일이 나타나는 경우가 0건이다.
- **SC-004**: 앱의 모든 화면을 점검했을 때 감사 기록을 보거나 내보내는 경로가 0개다.
- **SC-005**: 원문 열람이 거부된 시험에서 원문이 화면에 보이는 경우가 0건이다.
- **SC-006**: FR-011의 mock 경우를 서버 없이 모두 재현할 수 있다.

## Assumptions

- 감사 기록을 남기는 일(열람·재시도·점검 요청·전송·종료)은 모두 서버가 하며 앱은 따로 기록을 보내지 않는다(백엔드 spec 006 FR-001~006).
- 현황 API는 학급 식별자와 세 건수만 준다(api-v0.10 `GET /admin/inquiry-status`). 학급 표시 이름은 이미 있는 관리자 학급 목록에서 가져온다.
- 세 묶음의 화면 이름은 앱의 기존 표기와 맞춘다: 서버 `waiting` → "답변 대기", `confirmed` → "교사 확인", `answered` → "답변 완료". Figma ADM-4의 표기가 다르면 plan에서 Figma를 따른다.
- 타임라인은 F2가 만든 것을 그대로 쓴다. 서버 처리 단계 이력에 감사 항목이 섞여 오지 않는다(백엔드 spec 006 FR-012).
- 앱 사본 API 명세는 api-v0.8이다. 이 기능 전에 api-v0.10을 받아 오며, v0.9·v0.10의 다른 변경도 함께 확인한다(plan).
- 관리자 하단 탭(ADM-4 자리)이 아직 없으면 이 기능에서 만든다. 탭 구성은 `docs/ia.md` 하단 탭 표를 따른다.
