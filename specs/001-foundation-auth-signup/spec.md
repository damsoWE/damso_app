- Q: 세션 갱신이 거부되면 어디로 보내나? → A: 로그인 화면(C-1). 저장된 갱신 수단이 아예 없을 때와 로그아웃·탈퇴·비밀번호 재설정 완료 뒤에는 시작 화면(C-0).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 초대 코드로 가입하고 이메일 인증을 마친다 (Priority: P1)

학교에서 초대 코드를 받은 학부모나 교사가 앱을 처음 열고 "초대코드로 가입하기"를 누른다. 초대 코드·이름·이메일·비밀번호를 입력하고 약관에 동의한 뒤, 메일로 받은 6자리 인증 코드를 입력하면 가입이 끝나고 바로 로그인된다. 담소 이용 안내(C-6)를 확인하면 자기 역할의 홈으로 들어간다. 역할 선택·학교 검색은 없다 — 코드가 역할과 학급·학생을 정한다.

**Why this priority**: 공개 가입 경로가 없으므로 이 흐름이 없으면 교사·학부모 누구도 앱을 쓸 수 없다.

**Independent Test**: mock 실행에서 유효한 초대 코드로 가입 → 인증 코드 입력 → 이용 안내 → 역할 홈까지 진행되는지, 그리고 틀린 코드·틀린 인증 코드·잠금 상태가 각각 정해진 화면으로 보이는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 초대코드 입력(F1-1), **When** 유효한 학부모 코드를 확인, **Then** 학부모 계정 만들기(F1-3)로, 유효한 교사 코드면 교사 계정 만들기(F1-3a)로 이동한다.
1a. **Given** 계정 만들기 화면, **When** 이름·이메일·비밀번호를 입력하고 약관에 동의, **Then** 이메일 인증 화면(C-2)으로 이동하고 인증 코드 유효 시간(10분)이 안내된다.
2. **Given** 이메일 인증 화면, **When** 맞는 6자리 코드를 입력, **Then** 가입이 끝나 로그인 상태가 되고 담소 이용 안내(C-6)를 거쳐 서버가 알려 준 역할의 홈으로 이동한다.
3. **Given** 초대코드 입력, **When** 없는·만료된·사용된 코드를 확인, **Then** 사유를 구분하지 않는 같은 안내("코드를 확인해 주세요")가 보이고 다시 입력할 수 있다(F1-2).
4. **Given** 코드 입력이 5회 실패해 잠긴 상태, **When** 다시 확인, **Then** 코드 입력 잠금 화면(F1-2b)이 보이고 남은 대기 시간이 안내된다.
5. **Given** 이메일 인증 화면, **When** 인증 코드 재발송을 누름, **Then** 새 코드가 발송되었다고 안내되고, 60초가 지나기 전에는 다시 누를 수 없다.
6. **Given** 가입 입력 화면, **When** 형식에 맞지 않는 값(코드 10자리가 아님, 비밀번호 정책 위반, 이름 비었음, 약관 미동의)을 입력, **Then** 서버에 보내기 전에 해당 입력란에 안내가 보이고 진행 버튼이 동작하지 않는다.
7. **Given** 서버가 입력 오류를 필드별로 알려 줌, **When** 그 응답을 받음, **Then** 각 필드 아래에 서버의 안내 문구가 표시된다.

### User Story 2 - 로그인하고 역할별 홈으로 들어가며, 세션이 조용히 유지된다 (Priority: P1)

가입한 사용자가 이메일과 비밀번호로 로그인하면 역할(학부모·교사·슈퍼 관리자)에 맞는 홈으로 들어간다. 앱을 다시 열면 로그인 상태가 이어진다. 사용 중에 접근 권한이 만료되면 앱이 사용자 몰래 세션을 갱신하고 하던 작업을 이어 간다. 갱신이 불가능하면(14일 미사용, 다른 곳에서 세션 폐기 등) 저장된 로그인 정보를 지우고 로그인 화면으로 돌려보낸다.

**Why this priority**: 모든 보호된 화면의 전제다. F0의 세션 처리(갱신 경로·실패 시 로그아웃)가 여기서 검증된다.

**Independent Test**: mock 실행에서 역할별 계정으로 로그인해 각 홈으로 가는지, 접근 권한 만료 응답 뒤 자동 갱신·재시도가 되는지, 갱신 실패 시 로그인 화면으로 돌아가는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 로그인 화면(C-1), **When** 맞는 이메일·비밀번호로 로그인, **Then** 학부모는 학부모 홈, 교사는 교사 홈, 슈퍼 관리자는 관리자 홈으로 이동한다.
2. **Given** 로그인 화면, **When** 틀린 비밀번호 또는 없는 이메일로 로그인, **Then** 두 경우 모두 같은 안내("이메일 또는 비밀번호가 올바르지 않습니다.")가 보인다.
3. **Given** 연속 실패로 대기 중인 계정, **When** 로그인 시도, **Then** 로그인 대기 화면(C-1a)에 서버가 알려 준 남은 대기 시간이 보이고, 그 시간이 지나기 전에는 다시 시도할 수 없다.
4. **Given** 로그인 상태로 앱을 종료했다가 14일 안에 다시 엶, **When** 앱이 시작, **Then** 로그인 화면을 거치지 않고 역할 홈으로 들어간다.
5. **Given** 사용 중 접근 권한이 만료됨, **When** 화면이 데이터를 요청, **Then** 사용자는 오류를 보지 않고 요청이 한 번 다시 시도되어 정상 화면이 보인다.
6. **Given** 세션 갱신이 거부됨(만료·폐기·재사용 탐지), **When** 갱신 시도, **Then** 저장된 로그인 정보가 지워지고 로그인 화면(C-1)으로 이동한다.
7. **Given** 로그인되지 않은 상태, **When** 보호된 화면으로 이동하려 함, **Then** 시작 화면으로 돌아간다.
8. **Given** 로그인한 학부모, **When** 교사·관리자 전용 화면으로 이동하려 함, **Then** 자기 역할 홈으로 돌아간다.

### User Story 3 - 슈퍼 관리자가 학급·학생을 등록하고 초대 코드를 발행한다 (Priority: P1)

슈퍼 관리자가 로그인하면 관리자 홈이 열린다. 학급(학년·반)을 만들고, 학급에 학생 이름을 등록한다. 학급에 담임 초대 코드를, 학생마다 학부모 초대 코드를 발행한다. 발행된 코드 원문은 발행 직후 화면에서 한 번만 보이고 다시 볼 수 없다. 발행 현황에서 코드별 상태(미사용·사용됨·만료·무효)를 본다. 요청을 받으면 재발행하고, 이전 코드는 즉시 무효가 된다는 확인을 거친다.

**Why this priority**: 코드가 없으면 아무도 가입할 수 없다. 시연에서 가입 흐름 전에 반드시 필요하다.

**Independent Test**: mock 실행에서 관리자 계정으로 학급 생성 → 학생 등록 → 교사·학부모 코드 발행 → 원문 1회 표시 → 발행 현황 조회 → 재발행 확인 흐름이 동작하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 관리자 홈, **When** 학년(1~6)·반(1~20)을 입력해 학급을 추가, **Then** 학급 목록에 새 학급이 담임 연결 여부·학생 수와 함께 보인다.
2. **Given** 이미 있는 학년·반, **When** 같은 학급을 추가, **Then** 서버 안내가 보이고 학급이 중복 생성되지 않는다.
3. **Given** 학급 상세, **When** 학생 이름 여러 명(한 번에 최대 40명)을 등록, **Then** 학생 명단에 보호자 연결 여부와 함께 보인다.
4. **Given** 담임이 없는 학급, **When** 교사 초대 코드를 발행, **Then** 발행 완료 화면(ADM-3t)에 10자리 코드와 만료 시각이 보이고, 이 화면을 떠나면 원문을 다시 볼 수 없다는 안내가 있다.
5. **Given** 보호자가 없는 학생, **When** 학부모 초대 코드를 발행, **Then** 발행 완료 화면(ADM-3)에 코드가 한 번만 보인다.
6. **Given** 미사용 코드가 있는 대상, **When** 재발행을 누름, **Then** "이전 코드는 즉시 무효가 됩니다" 확인(ADM-6)을 거친 뒤에만 새 코드가 발행된다.
7. **Given** 담임이 이미 있는 학급 또는 보호자가 이미 있는 학생, **When** 코드 발행 시도, **Then** 서버 안내가 보이고 코드가 발행되지 않는다.
8. **Given** 학급 선택, **When** 발행 현황을 열람, **Then** 코드별 종류·대상 학생·상태·발행·만료·사용 시각이 보이고 코드 원문은 없다.

### User Story 4 - 학부모가 홈에서 담임을 보고, 자녀를 추가로 연결한다 (Priority: P2)

학부모는 홈에서 연결된 자녀와 각 자녀 담임의 공개 프로필(표시 이름·소개)을 본다. 담임이 아직 없으면 그 상태가 안내된다. 둘째 자녀부터는 마이페이지 > 연결된 자녀(F1-4)에서 초대 코드를 입력해 추가로 연결한다.

**Why this priority**: 문의 상대를 알려 주지만, 가입·로그인 없이는 의미가 없고 문의 작성(F2) 자체는 이 화면 없이도 설계할 수 있다.

**Independent Test**: mock 실행에서 자녀 1명·2명·담임 없음 상태의 학부모 홈과, 자녀 추가 성공·실패·잠금을 확인한다.

**Acceptance Scenarios**:

1. **Given** 자녀가 연결된 학부모, **When** 홈을 엶, **Then** 자녀 이름·학년·반과 담임의 표시 이름·소개가 보이고, 담임 이메일은 어디에도 보이지 않는다.
2. **Given** 자녀의 학급에 담임이 아직 없음, **When** 홈을 엶, **Then** "담임 선생님이 아직 연결되지 않았습니다"류의 안내가 그 자녀 카드에 보인다.
3. **Given** 자녀가 둘 이상, **When** 자녀 선택(F2-1a)을 엶, **Then** 자녀를 골라 홈에 보이는 자녀를 바꿀 수 있다.
4. **Given** 연결된 자녀 화면, **When** 유효한 학부모 초대 코드를 입력, **Then** 자녀가 목록에 추가된다.
5. **Given** 연결된 자녀 화면, **When** 무효한 코드·교사 코드·이미 보호자가 있는 학생의 코드를 입력, **Then** 사유를 구분하지 않는 같은 안내가 보인다.

### User Story 5 - 교사가 공개 프로필을 관리하고 학부모 연결 현황을 본다 (Priority: P2)

교사는 마이페이지에서 공개 프로필(표시 이름, 소개 60자)을 수정하고, 학부모 연결 현황(F3-10)에서 담당 학급 학생별로 학부모가 연결되었는지를 본다.

**Why this priority**: 학부모에게 보이는 정보와 학급 상황을 교사가 관리하지만, 문의 흐름의 필수는 아니다.

**Independent Test**: mock 실행에서 프로필 저장·글자 수 초과 거부와 연결 현황 목록(연결됨·미연결)을 확인한다.

**Acceptance Scenarios**:

1. **Given** 공개 프로필 편집(F3-9), **When** 표시 이름(1~20자)과 소개(60자 이하)를 저장, **Then** 저장된 값이 다시 열었을 때 보인다.
2. **Given** 공개 프로필 편집, **When** 소개가 60자를 넘음, **Then** 입력란에 남은/초과 글자 수가 보이고 저장되지 않는다.
3. **Given** 학부모 연결 현황, **When** 화면을 엶, **Then** 담당 학급과 학생별 연결됨·미연결이 보이고 학부모 이름·이메일은 보이지 않는다.

### User Story 6 - 비밀번호를 재설정한다 (Priority: P2)

비밀번호를 잊은 사용자가 로그인 화면에서 비밀번호 재설정을 누르고 이메일을 입력하면, 가입 여부와 관계없이 같은 안내가 보인다. 메일로 받은 6자리 코드를 확인하고 새 비밀번호를 정하면, 모든 기기에서 로그아웃된다는 안내와 함께 완료 화면이 보인다. 마이페이지의 "비밀번호 변경"도 같은 흐름을 쓴다.

**Why this priority**: 초대 코드는 1회용이라 계정을 잃으면 다시 가입하기 어렵다. 다만 가입·로그인 이후 단계다.

**Independent Test**: mock 실행에서 이메일 입력 → 코드 확인 → 새 비밀번호 → 완료, 그리고 틀린 코드·만료·잠금 화면을 확인한다.

**Acceptance Scenarios**:

1. **Given** 재설정 이메일 입력(C-3), **When** 어떤 이메일이든 입력, **Then** 같은 안내("입력한 이메일로 안내를 보냈습니다")가 보이고 코드 입력(C-3b)으로 이동한다.
2. **Given** 코드 입력, **When** 맞는 코드, **Then** 새 비밀번호 설정(C-4)으로 이동한다.
3. **Given** 코드 입력, **When** 만료되었거나 5회 실패로 잠김, **Then** C-3c 화면에서 코드를 다시 받거나 로그인으로 돌아갈 수 있다.
4. **Given** 새 비밀번호 설정, **When** 정책(영문+숫자 포함 8~64자)에 맞는 비밀번호를 저장, **Then** 완료 화면(C-5)이 보이고, 로그인한 본인 계정을 재설정했다면 이 기기도 로그아웃되어 시작 화면에서 다시 로그인한다(다른 계정을 재설정했다면 지금 세션은 유지).

---

### User Story 7 - 마이페이지에서 내 정보·로그아웃·탈퇴를 관리한다 (Priority: P3)

사용자는 마이페이지에서 이름·이메일·역할을 보고 이름을 수정한다. 로그아웃하면 이 기기만 로그아웃된다. 교사·학부모는 현재 비밀번호를 다시 입력해 회원 탈퇴할 수 있다. 슈퍼 관리자 마이페이지에는 탈퇴 메뉴가 없다.

**Why this priority**: 시연 필수는 아니지만 계정 수명 주기를 완결한다.

**Independent Test**: mock 실행에서 이름 수정, 로그아웃 후 시작 화면, 탈퇴 비밀번호 오류·성공을 확인한다.

**Acceptance Scenarios**:

1. **Given** 마이페이지, **When** 엶, **Then** 본인 이름·이메일·역할이 보인다(교사·학부모는 연결된 학급 정보도 함께).
2. **Given** 계정 정보, **When** 이름을 1~20자로 수정해 저장, **Then** 새 이름이 보인다.
3. **Given** 마이페이지, **When** 로그아웃, **Then** 이 기기의 로그인 정보가 지워지고 시작 화면으로 이동한다. 서버 호출이 실패해도 기기의 로그인 정보는 지운다.
4. **Given** 회원 탈퇴 확인(C-8), **When** 틀린 비밀번호로 탈퇴, **Then** 탈퇴되지 않고 서버 안내가 보인다.
5. **Given** 회원 탈퇴 확인, **When** 맞는 비밀번호로 탈퇴, **Then** 로그인 정보가 지워지고 시작 화면으로 이동한다.

### User Story 8 - 서버 없이 mock으로 모든 상태를 시연한다 (Priority: P2)

개발자·디자이너·심사자가 서버 없이 앱을 실행해, 정상 흐름뿐 아니라 오류·잠금·권한 없음·세션 만료 상태까지 화면으로 확인한다.

**Why this priority**: 백엔드와 독립적으로 화면을 만들고 검증하는 수단이다(프로젝트 아키텍처 규칙).

**Independent Test**: mock 실행만으로 아래 시나리오를 모두 재현할 수 있는지 확인한다.

**Acceptance Scenarios**:

1. **Given** mock 실행, **When** 정해진 시연용 입력을 넣음, **Then** 로그인 성공(역할 3종)·로그인 실패·로그인 대기·코드 오류·코드 잠금·인증 코드 오류를 각각 재현할 수 있다.
2. **Given** mock 실행, **When** 보호된 화면 데이터를 요청, **Then** 접근 권한 만료 → 자동 갱신 → 재시도 성공 흐름과, 갱신 실패 → 로그인 화면 흐름을 재현할 수 있다.
3. **Given** mock 실행, **When** 권한 없는 대상에 접근, **Then** 권한 없음 안내가 보인다.

---

### Edge Cases

- 가입 입력 후 인증 코드를 기다리는 사이 초대 코드가 재발행·만료되면, 인증 코드를 맞게 입력해도 "코드를 확인해 주세요" 안내와 함께 초대 코드 입력으로 돌아간다.
- 이미 가입된 이메일로 가입을 시도해도 화면은 평소와 같이 인증 코드 화면으로 넘어간다(서버가 가입 여부를 드러내지 않음). 그 이메일로는 안내 메일만 간다.
- 인증 코드 화면에서 앱을 종료하면 다시 열었을 때 가입 입력부터 다시 시작한다(대기 중인 가입 식별자는 기기에 오래 보관하지 않는다).
- 초대 코드 입력은 소문자·공백을 자동으로 대문자·공백 제거로 바꿔 보여 준다.
- 문의 본문이 아닌 짧은 입력에도 이모지 등 글자 수 계산 차이가 있을 수 있어, 글자 수 상한의 최종 판단은 서버 응답을 따른다.
- 대기·잠금 화면의 남은 시간은 서버가 알려 준 값으로 시작해 화면에서 줄어들며, 0이 되면 다시 시도 버튼이 활성화된다. 서버가 남은 시간을 주지 않으면 일반 안내("잠시 후 다시 시도해 주세요")만 보인다.
- 네트워크가 끊기거나 서버가 응답하지 않으면 공통 오류 안내와 다시 시도 버튼이 보이고, 입력하던 값은 지워지지 않는다.
- 여러 요청이 동시에 접근 권한 만료를 받아도 세션 갱신은 한 번만 일어나고, 나머지 요청은 그 결과로 다시 시도된다.
- 다른 기기에서 비밀번호를 재설정하거나 탈퇴해 이 기기 세션이 끊기면, 다음 요청에서 로그인 화면으로 이동한다.
- 학부모의 자녀들이 서로 다른 학급이면 자녀별로 각자의 담임이 보인다.
- 슈퍼 관리자 화면 어디에도 문의 본문·답변이 나오지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

**F0 공통 기반 — 오류 표시**

- **FR-001**: 앱은 서버 오류 응답의 안내 문구(`message`)만 사용자에게 보여 MUST 하며, 예외 내용·스택트레이스·내부 코드명을 화면에 표시하지 MUST NOT 한다.
- **FR-002**: 서버가 입력 오류를 필드별로 알려 주면, 앱은 해당 입력란 아래에 그 안내를 표시 MUST 한다.
- **FR-003**: 서버가 시도 제한(대기·잠금)을 알리면, 앱은 남은 시간을 표시하고 그 시간이 지나기 전에는 다시 시도할 수 없게 MUST 한다.
- **FR-004**: 서버 안내 문구를 받지 못한 오류(네트워크 끊김·시간 초과 등)에는 고정된 일반 안내와 다시 시도 수단을 보여 MUST 한다.
- **FR-005**: 앱은 비밀번호·초대 코드·인증 코드·세션 정보와 입력값을 로그·크래시 리포트·분석 이벤트로 내보내지 MUST NOT 한다.

**F0 공통 기반 — 세션**

- **FR-006**: 앱은 로그인·가입 완료 시 받은 세션을 유지하고, 장기 갱신 수단은 OS 보안 저장소에만, 단기 접근 수단은 메모리에만 둬야 MUST 한다.
- **FR-007**: 접근 권한 만료 응답을 받으면 앱은 세션을 한 번 갱신하고 원래 요청을 한 번만 다시 시도 MUST 한다. 동시에 여러 요청이 만료를 받아도 갱신은 한 번만 한다.
- **FR-008**: 세션 갱신이 거부되면 앱은 저장된 세션을 모두 지우고 로그인 화면(C-1)으로 이동 MUST 한다.
- **FR-009**: 앱 시작 시 저장된 갱신 수단이 있으면 세션을 복구해 역할 홈으로, 없으면 시작 화면으로, 서버가 복구를 거부하면(세션 만료) 로그인 화면으로 보낸다. 네트워크 오류·서버 일시 오류(5xx·시도 제한)로 복구하지 못하면 저장된 갱신 수단을 지우지 않고 "연결할 수 없음 + 다시 시도"를 보인다(오프라인에서 로그인이 풀리지 않게).
- **FR-010**: 화면 접근은 로그인 여부와 서버가 알려 준 역할로 한 곳에서 제어한다. 로그인 전에는 시작·로그인·가입·비밀번호 재설정 화면만, 로그인 후에는 자기 역할의 화면만 열린다. 이 제어는 편의를 위한 것이며 권한의 최종 판단은 서버다.

**F0 공통 기반 — API 계약과 mock**

- **FR-011**: 앱은 `docs/api/openapi.yaml`(api-v0.3)의 경로·요청·응답 형식을 따라야 MUST 한다. 이 사본은 직접 수정하지 않는다.
- **FR-012**: 모든 화면은 서버 없이 mock으로 실행할 수 있어야 MUST 하며, mock은 정상 응답 외에 접근 권한 만료(→ 갱신 → 재시도), 갱신 실패, 권한 없음, 입력 오류(필드별), 시도 제한(남은 시간 포함)을 재현할 수 있어야 MUST 한다.
- **FR-013**: 기존 뼈대 기능(문의 목록·이력·답변)의 mock은 이 작업에서 동작이 깨지지 않아야 한다. 해당 기능의 명세 반영은 각 기능(F2~F5) 작업에서 한다.

**F1 가입·이메일 인증**

- **FR-014**: 가입 입력은 초대 코드·이름·이메일·비밀번호·약관 동의뿐이다. 전화번호·주소 등 연락처 입력란이나 역할·학교·학급·학생 선택을 두지 MUST NOT 한다.
- **FR-015**: 앱은 서버에 보내기 전에 다음 형식을 검사한다: 초대 코드 10자리(영문 대문자·숫자, 0·O·1·I·L 제외, 소문자는 대문자로 바꿈), 이름 1~20자, 이메일 형식, 비밀번호 영문·숫자 각 1자 이상 포함 8~64자, 약관 동의 필수.
- **FR-016**: 초대 코드 실패는 사유(없음·만료·사용됨·대상 불일치)를 구분하지 않는 같은 안내로 보여 MUST 한다.
- **FR-017**: 가입 입력을 보내면 이메일 인증 화면으로 이동하고, 6자리 코드를 맞게 입력하면 가입이 확정되어 로그인 상태가 된다. 가입 직후에는 담소 이용 안내(C-6)를 한 번 보여 주고 역할 홈으로 이동한다.
- **FR-018**: 인증 코드 재발송은 60초에 한 번만 누를 수 있다. 재발송하면 이전 코드는 무효라는 안내를 보인다.
- **FR-019**: 가입 흐름은 Figma를 따른다. 초대 코드 입력(F1-1)에서 코드를 먼저 확인하고, 서버가 알려 준 역할에 따라 학부모용(F1-3) 또는 교사용(F1-3a) 계정 정보 화면으로 이동한다. 초대 코드 입력(F1-1)에서는 가입할 이메일도 함께 받는다 — 서버가 코드 확인 실패를 이메일 기준으로 세고 가입 1단계 실패와 합산하기 때문이다. 이 이메일은 계정 정보 단계에서 바꾸지 않고 그대로 쓴다. 코드 확인 실패·잠금은 F1-2·F1-2b로 안내한다. 계정 정보 단계에서 코드가 무효가 되면(그사이 재발행·만료) FR-016 안내와 함께 F1-1로 돌아간다(입력값 유지).

**F1 로그인·세션**

- **FR-020**: 로그인 실패는 없는 이메일·틀린 비밀번호를 구분하지 않는 같은 안내로 보인다.
- **FR-021**: 로그인 대기 상태에서는 서버가 알려 준 남은 시간을 대기 화면(C-1a)에 보이고, 대기 횟수·시간 규칙은 서버를 따른다(앱이 횟수를 세거나 "5회 10분" 같은 고정값을 표시하지 않는다).
- **FR-022**: 로그아웃은 이 기기만 로그아웃한다. 서버 호출 결과와 관계없이 기기의 세션은 지운다.

**F1 비밀번호 재설정**

- **FR-023**: 재설정 요청은 가입 여부와 관계없이 같은 안내를 보인다.
- **FR-024**: 재설정 코드 확인과 새 비밀번호 설정은 별도 단계다. 코드 만료·5회 실패 잠금은 C-3c 화면으로 안내하고 코드 다시 받기·로그인으로 돌아가기를 제공한다.
- **FR-025**: 비밀번호를 재설정하면 모든 기기에서 로그아웃된다는 사실을 완료 화면에 안내하고, 재설정한 계정이 이 기기에 로그인한 계정이면 이 기기의 세션도 지운다.

**F1 학부모**

- **FR-026**: 학부모 홈은 연결된 자녀별로 자녀 이름·학년·반과 담임 공개 프로필(표시 이름·소개)을 보인다. 담임이 없으면 그 상태를 안내한다. 자녀가 없으면 자녀 추가를 안내한다.
- **FR-027**: 학부모는 연결된 자녀 화면에서 초대 코드를 입력해 자녀를 추가 연결할 수 있다. 실패 안내·잠금은 FR-016·FR-003을 따른다.
- **FR-028**: 학부모 홈의 문의 관련 영역(문의 작성·최근 문의)은 이 spec의 범위가 아니다(F2). 이 spec에서는 자리만 두거나 숨긴다.

**F1 교사**

- **FR-029**: 교사는 공개 프로필(표시 이름 1~20자, 소개 0~60자)을 조회·수정할 수 있다. 사진은 없다.
- **FR-030**: 교사는 담당 학급과 학생별 학부모 연결 여부(연결됨·미연결)를 볼 수 있다. 학부모 이름·이메일은 표시하지 않는다.
- **FR-031**: 교사 홈은 이 spec에서 로그인 후 진입 화면 역할만 한다. 문의 관련 내용은 F2 이후 범위다.

**F1 슈퍼 관리자**

- **FR-032**: 슈퍼 관리자는 학급 목록(학년·반·담임 연결 여부·학생 수)을 보고, 학급(학년 1~6, 반 1~20)을 추가할 수 있다.
- **FR-033**: 슈퍼 관리자는 학급의 학생 명단(이름·보호자 연결 여부)을 보고, 학생 이름을 한 번에 1~40명 등록할 수 있다.
- **FR-034**: 슈퍼 관리자는 학급의 교사 초대 코드와 학생별 학부모 초대 코드를 발행·재발행할 수 있다. 재발행 전에는 이전 미사용 코드가 즉시 무효가 된다는 확인을 거쳐 MUST 한다.
- **FR-035**: 발행된 코드 원문과 만료 시각은 발행 완료 화면에서 한 번만 보인다. 앱은 코드 원문을 기기에 저장하거나 다른 화면에서 다시 보여 주지 MUST NOT 한다. 단, 관리자가 발행 완료 화면에서 직접 누른 "복사"로 클립보드에 넣는 것은 허용한다(학교가 코드를 전달해야 하므로). 앱이 자동으로 복사하지는 않는다.
- **FR-036**: 슈퍼 관리자는 학급별 발행 현황(종류·대상 학생·상태·발행·만료·사용 시각)을 볼 수 있다.
- **FR-037**: 슈퍼 관리자 화면에는 문의 본문·답변이 나오지 MUST NOT 한다. API가 없는 화면(코드 발행 요청 목록 ADM-8, 교직원 명단 ADM-9, 문의 현황 ADM-4)은 이 spec의 범위가 아니다.

**F1 마이페이지(공통)**

- **FR-038**: 사용자는 마이페이지에서 본인 이름·이메일·역할을 보고, 이름(1~20자)을 수정할 수 있다. 다른 사용자의 이메일은 어떤 화면에도 표시하지 MUST NOT 한다.
- **FR-039**: 교사·학부모는 현재 비밀번호를 다시 입력해 회원 탈퇴할 수 있다. 탈퇴되면 세션을 지우고 시작 화면으로 이동한다. 슈퍼 관리자 마이페이지에는 탈퇴 메뉴가 없다.
- **FR-040**: 마이페이지의 "비밀번호 변경"은 비밀번호 재설정 흐름(C-3)으로 이동한다.

**공통 화면 상태**

- **FR-041**: 데이터를 불러오는 모든 화면은 로딩·빈 목록·오류(다시 시도) 상태를 가진다. 진행 버튼은 요청 중 다시 누를 수 없다.

### Key Entities *(include if feature involves data)*

- **세션**: 로그인·가입 완료로 생긴 이 기기의 로그인 상태. 역할(학부모·교사·슈퍼 관리자), 단기 접근 수단(메모리), 장기 갱신 수단(보안 저장소). 갱신마다 바뀐다.
- **오류 안내**: 서버가 준 오류 종류, 사용자에게 보일 안내 문구, 필드별 안내 목록, 다시 시도까지 남은 시간(있을 때).
- **대기 중인 가입**: 가입 입력 후 인증 코드 입력까지의 상태. 가입 식별자와 인증 코드 유효 시간. 가입이 끝나거나 화면을 벗어나면 사라진다.
- **내 정보**: 이름, 본인 이메일, 역할.
- **자녀(학부모 기준)**: 학생 이름, 학급(학년·반), 담임 공개 프로필(없을 수 있음).
- **교사 공개 프로필**: 표시 이름, 소개 문구.
- **담당 학급(교사 기준)**: 학년·반, 학생별 보호자 연결 여부.
- **학급(관리자 기준)**: 학년·반, 담임 연결 여부, 학생 수.
- **학생(관리자 기준)**: 이름, 보호자 연결 여부.
- **발행된 초대 코드**: 코드 원문과 만료 시각. 발행 직후 한 번만 존재한다.
- **초대 코드 현황**: 종류(교사·학부모), 대상 학생(학부모 코드만), 상태(미사용·사용됨·만료·무효), 발행·만료·사용 시각. 원문 없음.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 초대 코드를 받은 교사·학부모가 메일 수신 시간을 빼고 3분 안에 가입·이메일 인증을 마치고 역할 홈에 도착한다.
- **SC-002**: 로그인한 사용자는 역할과 다른 홈·화면에 한 번도 도달하지 않는다(역할 3종 × 보호 화면 전체 확인).
- **SC-003**: 사용 중 접근 권한이 만료되어도 사용자에게 오류가 보이지 않고 요청이 이어지는 비율 100%. 갱신이 거부되면 100% 로그인 화면으로 이동하고 저장된 로그인 정보가 남지 않는다.
- **SC-004**: 어떤 오류 상황에서도 화면에 예외 내용·스택트레이스·내부 코드명이 보이지 않는다.
- **SC-005**: 가입·프로필·마이페이지 어느 화면에도 연락처 입력란이 0개이고, 다른 사용자의 이메일이 표시되는 화면이 0개다.
- **SC-006**: 발행된 초대 코드 원문을 발행 완료 화면 밖에서 앱이 다시 보여 주는 경로가 0개다(관리자가 직접 복사한 클립보드 내용은 제외).
- **SC-007**: 서버 없이(mock) User Story 1~8의 모든 Acceptance Scenario를 재현할 수 있다. 단, 앱 재시작 후 세션 복구(US2-4)는 실서버에서 확인한다 — mock은 세션을 기기에 저장하지 않는다.
- **SC-008**: 대기·잠금 상태에서 남은 시간이 지나기 전 다시 시도 버튼이 동작하는 경우가 0건이다.

## Assumptions

- **백엔드 의존 (FR-019, 해소)**: 초대 코드 확인 API가 api-v0.4에서 확정되었다(`POST /api/v1/auth/invite-codes/verify`, 요청 `inviteCode`·`email` 필수, 응답 `role`). 실패 횟수는 이메일 기준으로 가입 1단계와 합산되고 5회 실패 시 10분 잠금이다.
- 대기·잠금 규칙(로그인 30초~10분 단계적 대기, 코드 입력 5회 실패 10분 잠금, 인증·재설정 코드 10분 유효)은 서버가 정하고, 앱은 서버가 알려 준 남은 시간만 표시한다. Figma의 "5회 실패, 10분" 문구는 로그인 대기에 대해서는 서버 규칙에 맞춰 바꾼다.
- 약관(C-7) 문안은 임시 문안을 쓰고, 서버에는 동의 여부만 보낸다.
- 학부모 홈·교사 홈의 문의 관련 영역, 알림 목록, 알림 설정(F2-8, F3-8), 교사의 "관리자에게 재발행 요청"(F3-10a)은 이 spec 범위 밖이다. 재발행 요청은 API가 없으므로 오프라인 요청으로 본다.
- 슈퍼 관리자 계정은 서버에서 만들며, 앱에 생성 경로는 없다.
- 학교는 단일 학교로 본다. 학급 삭제·학생 명단 수정·담임 교체는 범위 밖이다.
- 서버 주소는 빌드 시 설정으로 주입하며, API 기본 경로(`/api/v1`)를 어디에 붙일지는 plan에서 정한다.
- 기존 뼈대 기능(문의 목록·이력·답변)의 임시 경로는 이 작업에서 고치지 않는다(FR-013).
- 공통 에러 형식·UUID·기본 거부 접근 통제는 백엔드 `specs/000-foundation`을 따른다.
